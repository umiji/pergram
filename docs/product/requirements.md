## 0. 可逆性マーカーの読み方

レビュー時の重み付けを判断するための記号。**🔒 が付いた項目だけ時間をかけて検討すればよい。**

| 記号 | 意味 | レビュー方針 |
|---|---|---|
| 🔒 | **不可逆**。後から変えるとデータ全件の再計算、URL全変更、法務やり直し等が発生 | 着手前に必ず確定させる |
| ⚠️ | **半可逆**。変更可能だが移行コストが大きい | 一度は検討する。迷ったら保守的に |
| 🔁 | **可逆**。いつでも変えられる | 決め打ちで進めてよい。走りながら直す |

## 1. 背景と目的

### 1.1 解決する課題
サプリメントは剤形・含有量・内容量・価格・**塩形態**がバラバラで、「同じ成分を同じ量だけ摂るのにいくらかかるか」を横並びで比較する手段が実質的に存在しない。特に日本市場には公的なラベルデータベースがない。

### 1.2 プロダクトの位置づけ 🔒
**効能を提案するツールではなく、事実を計算して並べるツール。**
- 症状や悩みから商品を推薦しない
- 独自の「総合スコア」「品質スコア」を作らない
- 提供するのは、含有量・価格・公的基準値・第三者認証という検証可能な数値と事実のみ

この位置づけは法務戦略そのものであり、崩すと薬機法リスクが一気に戻る。**不可逆。**

### 1.3 差別化の源泉 🔒

**重要な訂正（2026-08-05）**: 日本語圏でも「タンパク質1gあたり価格」で比較する記事は既に存在する（男前研究所、個人 note 等）。**「単価を計算すること」自体は差別化にならない。**

既存上位記事の構造的欠陥は3点:
1. **網羅していない** — 「おすすめ10選」形式。全製品を見たうえでの最安が分からない
2. **価格が更新されない** — 執筆時点の価格が残り続ける。プロテインは頻繁にセールする
3. **順位がアフィリエイト報酬に影響されている** — 上位記事はすべてアフィリエイト記事。ChatGPT で生成したと明記しているものもある

したがって pergram の差別化は **網羅性・鮮度・中立性** の3点に置く。これは [design/service.md](../design/service.md) の設計方針と既に整合している。

加えて、データ調達面の非対称性:
- 英語圏は NIH DSLD (CC0) により成分データが無料で入手でき、同種サービスが飽和
- **日本には公的なサプリラベル DB が存在しない** → 日本製品の成分データ整備そのものが参入障壁
- 中核資産は「日本流通サプリの構造化成分データ」

**最大の非対称性は製品ページの自動生成。** 競合は手書き記事のため製品ページを量産できないが、pergram は DB があるため製品数ぶんのページが自動で生まれる。ロングテールの総量で勝つ構造。

## 2. スコープ

### 2.1 決定済み前提
| 項目 | 決定 | 可逆性 |
|---|---|---|
| 対象市場 | **日本市場（＝日本の消費者が購入できる製品）から開始** | ⚠️ |
| 対象カテゴリ | 美容・筋トレ系の主要成分。マルチビタミンは後回し | 🔁 |
| 最初の入口 | Web サイト（Chrome 拡張は後続） | 🔁 |
| 収益 | アフィリエイト（楽天 → iHerb → Amazon の順） | 🔁 |

**注**: 「日本市場」＝日本の消費者が購入できる製品すべて。iHerb 日本語版経由で買える米国ブランドを含む。

**日本の個人輸入・iHerb 利用層は、本プロダクトの中核ターゲットである。** iHerb の成分横断検索は弱く、この層は為替と送料込みで単価を計算する習慣がある。数字で考える層であり、`pergram` の想定読者そのもの。

さらに重要なのは、**この層向けのデータは DSLD (CC0) でほぼ自動的に埋まる**こと。日本市場に絞っても手作業コストは想定より大幅に小さく、手作業は「日本ブランドのみ」という差別化部分に集中できる。

### 2.2 やること
| ID | 項目 | 可逆性 |
|---|---|---|
| S-01 | 成分あたりコスト比較 | 🔒 中核 |
| S-02 | 純度・含有率・**元素量換算**の表示 | 🔒 |
| S-03 | 品質ファセット（第三者認証・原産国・添加物等）によるフィルタ | 🔁 |
| S-04 | プレミアム幅の可視化（条件付き最安 − 無条件最安） | 🔁 |
| S-05 | 複数成分製品の評価（代替コスト法／バスケット最適化） | 🔁 |
| S-06 | RDA/UL 評価と超過警告（該当成分のみ） | 🔁 |
| S-07 | 価格アラート | 🔁 |
| S-08 | レビュー星評価の表示（出典明記） | 🔁 |
| S-09 | アクセス解析（GA4） | 🔁 |
| S-10 | 多言語対応（ja / en） | 🔒 設計のみ先行 |
| S-11 | Chrome 拡張 | 🔁 後続 |

### 2.3 やらないこと — 明示的に禁止 🔒
| ID | 項目 | 理由 |
|---|---|---|
| N-01 | 症状・不調・悩みの入力受付 | 「症状→成分→商品」の導線は医薬品的効能効果の暗示（薬機法） |
| N-02 | 成分の効能・効果に関する独自文章の生成 | 同上 |
| N-03 | 独自の総合スコア・品質スコア・加重平均ランキング | 重み付けが恣意的で、事実提示ではなく推薦になる |
| N-04 | ユーザーリクエストパスでの LLM 生成 | コストがトラフィックに比例／事前審査不可能 |
| N-05 | 健康状態・体調・服薬情報のサーバ保存 | GDPR 特別カテゴリ／要配慮個人情報に該当しうる |
| N-06 | 定期購入型 D2C アフィリエイト案件の主軸化 | 中立性の毀損と法務リスクの復活 |
| N-07 | 診断的表現（「あなたは◯◯が欠乏しています」等） | 医師法・薬機法 |
| N-08 | Amazon / iHerb のレビュー本文・星評価のスクレイピング転載 | 各社利用規約違反、著作権 |
| N-09 | **AGA・育毛・薄毛の文脈で成分を扱うこと** | 検索意図が 100% 効能であり pergram は答えられない。景表法のアフィリエイト広告に対する初の措置命令（2021年3月）は育毛剤事案であり、当局の注視が最も強い領域。クリニックが高額 CPC で入札する激戦区でもある |
| N-10 | 妊活・美容医療の文脈で成分を扱うこと | 同上 |

**成分そのものの除外ではなく、文脈の除外である。** 亜鉛は筋トレ文脈（ZMA 等）なら対象。育毛文脈では扱わない。

### 2.4 対象成分と、それに伴う制約 🔒

**重要**: 美容・筋トレ系の主要成分の多くは「日本人の食事摂取基準」に収載されておらず、RDA / UL が存在しない。栄養機能食品の定型文もビタミン13種・ミネラル6種程度にしか存在しない。
**成分によって使える比較軸が異なる**ことを前提にデータモデルを設計する。

| 成分 | 市場規模 | RDA/UL | 定型文 | 抽出難易度 | 初版 |
|---|---|---|---|---|---|
| ホエイ/ソイプロテイン | 最大 | タンパク質としてRDA/DGあり（ULなし） | なし | 中（表記ゆれ3通り） | **◎ P1（本命）** |
| クレアチン | 大 | なし | なし | 最易（純度ほぼ100%） | ◎ 先行して配管検証に使う |
| 鉄 | 中 | **両方あり** | あり | 易（要塩形態換算） | ◎ |
| 亜鉛 | 中 | **両方あり** | あり | 易（要塩形態換算） | ◎ |
| ビタミンC | 大 | あり | あり | 易 | ◎ |
| EAA / BCAA | 中 | なし | なし | 中（アミノ酸個別） | ○ |
| HMB | 中 | なし | なし | 易 | ○ |
| コラーゲン | 大 | なし | なし | 易 | ○ |
| ビオチン | 中 | RDAあり | あり | 易 | ○ |
| NMN / エクオール / プラセンタ | 中（高単価） | なし | なし | 易 | △ 法務リスク最大 |
| マルチビタミン | 大 | あり | あり | 難（成分数が多い） | 後回し |

- `ReferenceValue` が存在しない成分では、UI に「公的な推奨量・上限量は定められていない」と明示し、**推定値や独自の目安を表示しない**
- 美容系（NMN・コラーゲン・プラセンタ・エクオール）は薬機法の摘発が最も集中する領域。数値のみの提示を厳格に守る

#### キーワード調査の結果（2026-08-05, Semrush + Google KP）🔒

| クラスタ | 月間合計 | KD |
|---|---|---|
| ヘッド「プロテイン」 | 135K | 47% |
| ヘッド「クレアチン」 | 90.5K | 34% |
| **プロテイン コスパ系（4クエリ合算）** | **約 15K** | **18〜25%** |
| クレアチン コスパ系 | 約 0.5K | — |
| クレアチン 最安 | 10 | — |

**ヘッド層は攻略できない。** 「プロテイン」「クレアチン」の検索意図は効果・飲み方・選び方であり、pergram は薬機法上それらに答えられない。ヘッドは市場規模の指標としてのみ扱う。

**攻略可能なのはコスパ・比較・単価クラスタのみ。** そこではプロテインがクレアチンの約 30 倍。これが P1 をプロテインとする根拠。

#### 攻略順序 🔒
```
ロングテール → 製品ページ量産 → ヘッドクラスタ
```
新規ドメインで「プロテイン コスパ」に正面から挑んでも、TIPNESS・晋遊舎等の既存ドメイン評価に半年〜1年は勝てない。

| 狙う型 | 理由 |
|---|---|
| ブランド横断の単価比較（「エクスプロージョン ザバス 単価」） | 既存は単一記事内の10選。ブランド間の直接比較ページがない |
| 容量別（「プロテイン 3kg 単価」） | 大容量は価格差が大きく需要も明確 |
| 含有率軸（「タンパク質含有率 高い プロテイン」） | 単価と別軸で既存記事が弱い |
| **製品ページ（製品名 × 単価）** | **DB を持つ側だけが自動生成できる。最大の非対称性** |

## 3. 法規制要件（最優先制約）🔒

機能要件より優先する。実装時に迷ったら **より保守的な方**を選ぶ。

### 3.1 表現のホワイトリスト方式
成分の機能に言及する文章は、**自由記述を一切許さず、以下からの引用に限定する**。

| 出典 | 用途 |
|---|---|
| 栄養機能食品の規格基準に定められた定型文 | 成分 → 説明文の固定マッピング |
| 消費者庁「機能性表示食品」届出データベースの届出表示 | 出典明記のうえ引用 |
| 厚生労働省「日本人の食事摂取基準(2025年版)」 | RDA / AI / UL / EAR / DG の数値 |

実装: `nutrient_claims` テーブルに固定文言を持ち、コードから動的生成させない。定型文が存在しない成分には**何も表示しない**（空欄が正しい挙動）。

### 3.2 免責表示
全画面に常時表示。医療上の助言でないこと、医薬品でないこと、疾病の診断・治療・予防を目的としないこと、摂取判断は医師・薬剤師に相談すること。

### 3.3 アフィリエイト表示
- ステマ規制（景表法）対応として、アフィリエイトリンクを含むページに広告である旨を明示
- 各プログラム所定の文言を併記
- **ランキング順位がアフィリエイト報酬額に影響しないこと**を明記し、実際にそう実装する（並び順は常に指定指標のみで決定）

### 3.4 データ保護
- 年齢・性別・服用中サプリは **localStorage / IndexedDB のみ**。サーバへ送信しない
- サーバが保持してよいのはメールアドレスと監視製品IDのみ（価格アラート）
- GA4 には個人識別情報を送らない。EU/UK 配信時は Consent Mode v2 と Cookie 同意バナーが必要

## 4. 中核アルゴリズム 🔒

### 4.1 元素量換算（最重要）
ラベル記載量と、実際の元素・有効成分量は異なる。**換算せずに比較すると結果が根本的に誤る。**

例:
- 酸化マグネシウム 500mg ≒ 元素マグネシウム 約300mg
- グリシン酸マグネシウム 500mg ≒ 元素マグネシウム 約50mg
- フマル酸第一鉄 / 硫酸第一鉄 / ピロリン酸第二鉄で元素鉄の比率が異なる
- グルコン酸亜鉛 / ピコリン酸亜鉛 / 酸化亜鉛で同上

実装: `SaltForm` テーブルに (化合物, 対象元素, 元素含有率) を持ち、`amount_elemental` を必ず算出して保存する。
**後から導入するとデータ全件の再計算になるため、P0 で確定させる。**

同様の換算が必要なもの: 葉酸の DFE、ビタミンE のα-トコフェロール当量、ビタミンA のレチノール活性当量、ナイアシン当量、IU ⇔ mcg。

### 4.2 単一成分のコスパ計算 — 正規形と導出 🔒

#### 保存する独立変数は2つだけ
```
Product.serving_size_g          1食 / 1回分のグラム数（カプセル等は NULL 可）
Product.servings_per_unit       1容器あたりの回数
NutrientContent.amount_elemental  1 serving あたりの有効成分量（元素量換算後）
```

**それ以外はすべて導出する。冗長に保存しない。** 二重に持つと片方だけ更新され、必ず矛盾する。

| 求めたい値 | 式 |
|---|---|
| 100g あたり含有量 | `amount_elemental / serving_size_g × 100` |
| 含有率 (%) | 上記 ÷ 100 |
| 1食あたり含有量 | `amount_elemental` |
| **有効成分1単位あたり価格（主指標）** | `price / (amount_elemental × servings_per_unit)` |
| 1食あたり価格 | `price / servings_per_unit` |

#### per serving を比較の分母にしない 🔒
`serving`（1食 / 1粒）は**メーカーが任意に定義した単位**であり、製品を横断して比較できない。

- 1粒 500mg の製品と 250mg の製品では、per capsule 単価が 2倍に見えるが、2粒飲めば同量
- ザバス 1食 21g とエクスプロージョン 1食 30g は、そもそも別の量

**比較の分母にできるのは有効成分量のみ。** per serving は UI に補助表示してよいが、**ソートキーには絶対に使わない。**

#### この式は全カテゴリで共通 🔒
プロテイン固有・カプセル固有の計算は存在しない。変わるのは表示単位だけ。

| 成分 | 分母 | 表示 |
|---|---|---|
| プロテイン | タンパク質 g | ¥/g |
| クレアチン | クレアチン g | ¥/g |
| 亜鉛 | 元素亜鉛 mg | ¥/mg |
| ビタミンD | mcg（IU 換算後） | ¥/mcg |

#### カテゴリ固有テーブルを作らない 🔒
カテゴリごとにテーブルを増やす設計は破綻する（EAA はロイシン比率、コラーゲンは分子量、クレアチンは形態…と際限なく分岐するため）。
**カテゴリ差は表示設定 JSON で吸収する**（market 設定と同じ方式。§9.2）。

```json
"protein": {
  "primaryMetric": "cost_per_g",
  "secondaryMetrics": ["content_ratio", "cost_per_serving"],
  "displayUnit": "g"
},
"zinc": {
  "primaryMetric": "cost_per_mg",
  "secondaryMetrics": ["ul_percentage", "cost_per_serving"],
  "displayUnit": "mg"
}
```

新カテゴリの追加は JSON に1ブロック足すだけ。テーブル・クエリ・UI は変更しない。

#### 唯一のカテゴリ固有処理は「抽出時の正規化」
プロテインのラベルは「1食30gあたり24g」「100gあたり80g」「含有率71%」の3通りが混在する。
これは**DB の問題ではなくパイプラインの問題**。`normalize_protein()` として実装し、どの表記からも `serving_size_g` と `amount_elemental` に落とす。中間形式は **100g あたり g** とする（1食量に依存しないため）。

### 4.3 複数成分製品の評価 — 代替コスト法 🔁
**総合スコアは作らない。** 代わりに以下を計算する。

```
1. ユーザーが「欲しい成分」の集合 W を選択する
2. 複合製品 P に含まれる成分のうち、W に属するものだけを対象とする
   （W に無い成分は価値ゼロとして扱い、コストにも算入しない）
3. 各成分 n について、単一成分サプリの最安単価 min_cost(n) を引く
4. replacement_cost(P) = Σ (P に含まれる n の量 × min_cost(n))
5. premium(P) = P の価格 − replacement_cost(P)
```
UI 表示例: 「この製品は、同じ成分を個別に揃えるより 1日あたり 12円 安い」

前提として、上限は W の目標量でクリップする（目標超過分は価値ゼロ）。この扱いは UI で明示する。

### 4.4 バスケット最適化 🔁
ユーザーが目標成分量の集合を定義 → それを満たす製品組み合わせのうち総コスト最小のものを探索。
成分数・候補数が小さいうちは全探索でよい。大きくなったら貪欲法 + 局所探索。

### 4.5 プレミアム幅の可視化 🔁
```
premium_gap = min(cost | フィルタ条件あり) − min(cost | フィルタ条件なし)
```
表示例: 「第三者認証ありに絞ると +23円/日」「有機JASのみに絞ると +41円/日」
これは事実の提示であり、優劣の判断ではない。**「だから認証品を選ぶべき」等の文言は付けない。**

## 5. 品質ファクターの扱い 🔒

**方針: 合成しない。ファセット（フィルタ + バッジ）として並列表示する。**

| 種別 | 属性 | 扱い |
|---|---|---|
| 第三者検証 | Informed Sport, Informed Choice, NSF Certified for Sport, USP Verified, cGMP | バッジ + フィルタ |
| 認証 | 有機JAS, USDA Organic, Non-GMO Project | バッジ + フィルタ |
| ラベル記載事実 | 原産国, 製造国, 人工甘味料の有無, 添加物, アレルゲン, ベジタリアン対応, 剤形 | フィルタ |
| 化学形態 | クレアチン一水和物/HCl, 塩形態, キレート形態 | **事実として表示。優劣は述べない** |
| ユーザー評価 | 星評価・レビュー件数 | 出典明記で表示 |
| 独自スコア | — | **作らない** |

**化学形態について**: 「グリシン酸マグネシウムは吸収が良い」等は効能表現に接近するため書かない。形態を事実として記載し、元素量換算のみ行う。

## 6. データモデル

🔒 = スキーマ変更が全件再計算を伴う項目

```
Nutrient  🔒
  id                  string (PK)      # 例: "creatine", "vitamin_c"
  canonical_unit      enum(mg, mcg, g, IU)
  category            enum(vitamin, mineral, amino_acid, protein, other)
  has_reference_value bool             # RDA/UL が存在するか

NutrientI18n  🔒                        # 多言語は最初から別テーブル（§9）
  nutrient_id / locale / name / synonyms[]

SaltForm  🔒                            # §4.1
  id / nutrient_id / compound_name / elemental_ratio decimal / source

Product
  id                  string (PK)
```

## 7. データ調達パイプライン

### 7.1 成分レイヤー（静的・低頻度）
```
Tier A: 米国ブランド（iHerb 等で日本から購入可能なもの）
  DSLD API → 正規化 → 元素量換算 → 格納
  OCR 不要。CC0 のため商用利用可

Tier B: 日本ブランド（差別化の核）
  1. メーカー公式サイトの商品ページを取得
  2. 栄養成分表示が HTML → パーサで抽出（半数以上はここで済む見込み）
  3. 画像のみ → PaddleOCR (Apache-2.0) でテキスト化
                → LLM は「OCRテキスト → JSON」構造化のみ
  4. バリデーション（§7.3）
  5. 低信頼のみ人間レビュー

Tier C: ロングテール → 初版スコープ外
```
**OCR ライセンス注意** 🔒: YomiToku は CC BY-NC-SA 4.0 で商用利用に別途ライセンスが必要なため使用しない。PaddleOCR (Apache-2.0) を採用。

### 7.2 価格レイヤー（動的・日次）
- **楽天商品検索 API** を初期の主軸とする（無料・審査が軽い・`reviewAverage` / `reviewCount` も取得可）
- Amazon は Creators API（PA-API は 2026-05-15 廃止）。アクセス・維持に継続的な成約実績が必要なため初期は依存しない
- iHerb は公開 API なし。スクレイピング要否は §12 Q-05 で判断
- 実行基盤: GitHub Actions cron → JSON をコミット
- robots.txt と利用規約を必ず確認。レート制限を守る

### 7.3 バリデーション（必須）
| 検査 | 内容 |
|---|---|
| V-01 | 単位変換の整合性 |
| V-02 | 元素量換算後の値が妥当レンジか |
| V-03 | UL との照合（大幅超過は抽出ミスを疑う） |
| V-04 | 桁数チェック（1000倍 / 1000分の1 の取り違え） |
| V-05 | 同一ブランド内の一貫性 |
| V-06 | 前回スナップショットとの差分が閾値超なら要レビュー |

異常値のみ人間レビューキューへ。

## 9. 多言語対応 🔒

**後付けが最も高くつく領域。P0 で設計だけ済ませ、実装は後でよい。**

| 項目 | 方針 | 可逆性 |
|---|---|---|
| URL 構造 | `/ja/...` `/en/...` のサブパス方式を**初版から**採用。ルートは言語判定してリダイレクト | 🔒 後付けは全 URL 変更 = SEO 大損 |
| 文言 | すべて翻訳キー経由。ハードコード禁止 | 🔒 |
| 成分名・製品名 | `NutrientI18n` / `ProductI18n` の別テーブル。`name_ja` `name_en` のカラム持ちにしない | 🔒 |
| 数値・通貨・単位 | `Intl.NumberFormat` 等でロケール書式化。文字列連結禁止 | 🔒 |
| 法定表示 | 免責・広告表示は**地域ごとに別テキスト**（日本＝薬機法、EU＝Reg 1924/2006）。単純翻訳は不可 | 🔒 |
| 参照値 | `ReferenceValue.region` で切替（JP / US / EU） | 🔁 |
| hreflang / lang 属性 | 後から追加可 | 🔁 |
| 実際の翻訳作業 | P6 以降。まずは ja のみ埋める | 🔁 |
| ブランド表示名 | `pergram` で統一。ただし**ロケールキー経由**にしておき、将来の市場別ブランド名を可能にする | 🔁 |

### 9.1 `locale` と `market` を分離する 🔒

**表示言語と、適用される市場は独立した軸である。** これを1つの変数に潰すと後戻りできない。

| 軸 | 決めるもの | 保存先 |
|---|---|---|
| `locale` (ja / en) | 表示言語のみ | localStorage |
| `market` (JP / US) | **表示する merchant、参照値、免責文、通貨** | localStorage |

想定される組み合わせ:

| locale | market | 例 |
|---|---|---|
| ja | JP | 標準 |
| **en** | **JP** | **日本在住の外国人。楽天は普通に買えるので隠してはいけない** |
| ja | US | 米国在住の日本人。楽天を出しても無意味 |
| en | US | 標準 |

- 初回訪問時に `Accept-Language` と IP から**それぞれ独立に推定**し、どちらも個別に変更できる UI を置く
- **免責文・広告表示は `locale` ではなく `market` に紐づける。** 日本在住者が英語 UI で見ていても、適用されるのは日本の規制

### 9.2 market 設定はデータで持つ 🔒

コンポーネントに `if (locale === 'en')` を書き始めると分岐が増殖し、個人では保守できなくなる。**設定 JSON を回して描画し、条件分岐をゼロにする。**

```json
{
  "JP": {
    "merchants": ["rakuten", "amazon_jp", "iherb"],
    "referenceRegion": "JP",
    "disclosureKey": "disclosure.jp",
    "currency": "JPY",
    "claimSource": "nutrient_function_food"
  },
  "US": {
    "merchants": ["iherb", "amazon_us"],
    "referenceRegion": "US",
    "disclosureKey": "disclosure.us",
    "currency": "USD",
    "claimSource": null
  }
}
```

新しい市場を足すときは、このファイルに1ブロック追加するだけで済む状態を保つ。

### 9.3 日本語版と英語版は「翻訳」ではない 🔒

| | `/ja/` | `/en/` |
|---|---|---|
| 掲載製品 | 日本から購入可能なもの（`PriceSnapshot` に日本の merchant があるもの） | 米国から購入可能なもの |
| 参照値 | 日本人の食事摂取基準(2025年版) | 米国 DRI |
| 免責文 | 薬機法 + ステマ規制 | FTC endorsement disclosure + DSHEA |
| 定型文 | 栄養機能食品の規格基準 | 該当制度なし（表示しない） |

したがって:
- **成分ランキングページに hreflang を相互指定しない**（掲載製品が異なり等価ページではない）
- hreflang は「データの作り方」「このサイトについて」など**本当に等価なページのみ**
- 言語切替 UI の文言は「翻訳版へ移動」ではなく「**別の市場のデータを見る**」の意味にする

### 9.4 共用できる資産・できない資産

| | 共用 | 理由 |
|---|---|---|
| 成分データ（含有量） | ◎ 完全共用 | クレアチン 5g はどこでも 5g |
| 塩形態 → 元素量の換算テーブル | ◎ | 化学は国境を持たない |
| 第三者認証 | ◎ | Informed Sport 等は国際認証 |
| 価格 | △ | merchant ごとに独立。通貨・送料が別 |
| 参照値 (RDA/UL) | ✗ | 食事摂取基準 vs DRI で数値が異なる |
| 免責文・広告表示 | ✗ | 翻訳ではなく差し替え |
| 定型文（栄養機能食品） | ✗ | 日本固有の制度 |

**共用できないのは法務まわりのみ。** 資産の中核（成分データと換算ロジック）は 100% 共用できる。

### 9.5 `Product.country` は持たない 🔒

購入可能性は「その製品に、その市場の merchant の `PriceSnapshot` が存在するか」で決まる。
Product に国フラグを持たせると、複数市場で流通する製品（iHerb で売られる日本ブランド等）を表現できず、流通状況の変化にも追随できない。

```
日本から買える = EXISTS(PriceSnapshot WHERE merchant IN market.merchants AND in_stock)
```

## 11. アクセス解析（GA4）

### 11.1 制約 🔒
- 個人識別情報を送らない。年齢・性別は localStorage 保持であり GA4 にも送らない
- 健康関連の入力値をイベントパラメータに含めない
- EU/UK 配信時は Consent Mode v2 と同意バナーが必要

### 11.2 主要イベント設計 🔁
| イベント名 | パラメータ | 目的 |
|---|---|---|
| `nutrient_view` | nutrient_id | どの成分に需要があるか |
| `filter_apply` | filter_key, filter_value | 品質ファセットの利用実態 |
| `product_view` | product_id, brand, rank_position | 何位まで見られるか |
| `affiliate_click` | product_id, merchant, rank_position, cost_per_unit | **最重要 KPI** |
| `stack_add` / `stack_calculate` | nutrient_count | バスケット機能の利用率 |
| `price_alert_create` | product_id | リテンション施策の効果 |
| `premium_gap_view` | filter_key, gap_amount | プレミアム幅機能の価値検証 |
| `unit_convert` | from_unit, to_unit | 換算機能の需要 |

### 11.3 見るべき指標
- 成分別の `affiliate_click` / `nutrient_view` 比率 → 次に整備する成分の優先順位を決める
- `rank_position` の分布 → 上位何件までが実質的に見られているか
- `filter_apply` の内訳 → 品質ファセットのうちどれが実際に使われるか

本命はプロテインだが、**最も単純なデータで先に配管を通す**。クレアチンモノハイドレートは純度がほぼ100%で、内容量と価格だけで単価が出る（成分表の抽出が不要）。
プロテインから始めると、抽出の難しさとパイプラインのバグが混ざって切り分けられなくなる。
