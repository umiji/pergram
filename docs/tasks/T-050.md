## 目的

**8/31〜9/6 の Google 広告（110クリック / ¥2,316）で待機リスト登録が 0 件だった。**
D1 を直接確認して 0 件を確定済みであり、送信経路の不具合ではない。

原因の最有力は「需要が無い」ではなく **測っていた対象と、ページが誘導していた先が食い違っていた**ことである。

- LP のヒーローの CTA は **β版（製品一覧）への1本だけ**で、待機リストのボタンは出していない
  （`src/templates/lp/hero.js` の 🔒 コメント。2026-09-02 T-020、PO 指示の実験）
- 製品一覧側の待機リストの案内は **リストの後ろ**にあり、しかも**その場のフォームではなく別ページへのリンク**
  （`src/templates/products.js` の `waitlistBanner`）
- つまり広告で連れてきた人をβ版へ送り、そのうえで待機リスト登録を KPI にしていた

**このタスクは「メールアドレスという重い対価を、意思表示1クリックまで下げる」ことを行う。**
知りたいのは「このサービスの拡充を望む人がどれだけ居るか」であり、メールアドレスはその後段でよい。

## 禁止事項

- 🔒 **要望ボタンの押下数を画面に出さない。** 出すと「人気」の表示になり、`.claude/rules/pergram-ui-copy.md` の
  禁止語と景表法に触れる。押した本人へのフィードバック（ボタンの状態変化）だけにする
- 🔒 **要望の数を製品の並び順に一切使わない（N-03）。** 並び順を決めるのは常に有効成分1単位あたりの価格
- 🔒 **β版（製品一覧）へのリンクを LP から削除しない。** 2026-09-07 の PO 判断（下記 決定ログ）
- 🔒 **成分の効能・効果に触れる文言を書かない（N-02）。** ボタンも注記も「追加してほしいか」だけを問う
- 🔒 サーバへ新しい列を足さない。第1段階の計測は **GA4 イベントのみ**で行う。
  D1 のスキーマを変える必要が出たら、着手せず報告する（共通の停止条件 S-2）
- 🔒 自由記述の**本文**を GA4 へ送らない。書かれたかどうか（0/1）だけ（`.claude/rules/pergram-compliance.md`）
- 製品一覧の初期表示件数を変えない（**10件のまま**。2026-09-07 PO 判断）

### 2026-09-07 ヒーローのランキングカードは「価格情報・順位ともサンプル」と名乗る

  名乗る案 → PO が採らなかった。(b) 現状維持 → 何がサンプルなのかが伝わらないため却下
- 付帯条件: **オーケストレーターは、この表記が実態より控えめである旨を PO へ申し送った。**

- 出典: セッション内の PO 判断、成果物なし

### 2026-09-07 意思表示は成分単位ではなくサービス単位で問う
- 対象: 待機リスト / 製品一覧
- 決定: 第1段階のボタンは「他の成分・製品追加をリクエスト」とし、
  **サービス全体への要望**を1クリックで受ける。成分ごとの意思表示ボタンは作らない。
  成分の内訳は、押した人にだけ開く第2段階のアンケート（任意）で取る
- 却下案: 成分チップごとに意思表示ボタンを置く案 → PO の意図は
  「このサービスの機能拡充を望むか」であり、個別成分への評価ではないため却下。
  加えて製品単位のボタンは N-03（独自ランキング）と景表法の「人気」表示に触れやすい
- 出典: セッション内の PO 判断、成果物なし

### 2026-09-07 β版へのリンクは LP から削除しない
- 対象: LP / 導線
- 決定: 待機リスト登録を増やす目的で、LP からβ版（製品一覧）への導線を削除しない
- 却下案: LP からβ版リンクを削除して待機リストへ一本化する案 → β版は現時点で
  唯一ユーザーへ価値を届けている機能であり、計器（待機リスト）の数字のために
  製品を隠すことになるため却下。加えて広告の着地ページとして、
  広告文が約束した単価比較を提供できなくなる
- 出典: セッション内の PO 判断、成果物なし

### 2026-09-07 アンケートの回答はメールアドレスの段の送信に相乗りさせる
- 対象: 製品一覧 / 要望の段階
- 決定: アンケート（第2段）は送信時にサーバへ飛ばさず、回答を画面に保持しておき、
  メールアドレス（第3段）を送るときに1回の POST へまとめて載せる。
  メールアドレスを入れずに進んだ場合、回答はサーバに残らず GA4 の集計だけが残る
- 却下案: (a) アンケート送信の時点でサーバへ送る → 保存の鍵はメールアドレスしかなく
  （`waitlist` は email が主キー）、匿名の回答を保存するには**列か識別子を足す**必要がある。
  T-050 の禁止事項「サーバへ新しい列を足さない」と共通の停止条件 S-2 に触れる。
  (b) 段の順序をメール → アンケートにして LP と揃える → 順序は決定済み（変更不可）
- 付帯条件: 相乗りする項目は既存の6列の範囲だけ（`tests/request_flow_behavior.test.js` の
  「送信本文は保存してよい列の範囲だけ」が固定している）
- 出典: セッション内の判断、成果物なし

### 2026-09-07 段の操作は products.js に足さず request.js を新設する
- 対象: 製品一覧 / クライアントスクリプト
- 決定: 要望ボタンと段の開閉は `src/assets/request.js` に置き、`src/assets/products.js` へ足さない
- 却下案: `src/assets/products.js` に追記する → **同ファイルは絞り込みのフォームか製品リストが

### 2026-09-07 支援ウィジェットは製品一覧ページにも置く（1ページ1つは守る）

## 組織への指摘
- [規約]（実装担当）タスクの `## 申し送り` に「`tests/hero_ranking.test.js` の2件が着手前から落ちている」と
  書かれていたが実際は落ちておらず、起動時の指示で口頭に打ち消された。**申し送りは登録後に埋まる唯一の
  指示欄であるのに、内容が古くなったときに誰が直すかが決まっていない**（今回は指示欄と口頭指示が食い違った）
- [規約] 受け入れテストを実装より先に書く規約だが、完了条件が「要望ボタン」「段階」のような
  画面の言葉で書かれているため、機械が名指しするための目印（属性名）をテスト側が先に決めることになる。
  一方でタスクの `## 判断してよい範囲` は DOM 構造を実装の裁量としており、
  どちらが目印を決めるのかが規約からは読み取れない（今回はテスト側で決め、ファイル冒頭に明記した）
