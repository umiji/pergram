## 目的

**PO 報告: 「ボタンを押してもデータベースに登録されない」。オーケストレーターが本番で再現を確認した。**

### 何が起きているか

`src/assets/request.js` の `sendRequestSignal()` は、こう書かれている。

```js
if (readSignalId()) return;   // ← 保存済みなら二度と送らない（恒久）
const id = newSignalId();
if (!id) return;
writeSignalId(id);            // ← fetch の**前**に保存する。結果を見ない
try { fetch(...).catch(() => {}) } catch {}
```

**識別子を localStorage へ書くのが送信の前で、しかもその後の判定が「書いてあるなら送らない」なので、
最初の1回が失敗したブラウザは、以後 何度押しても永久に1行も残さない。**
失敗の理由は問わない（400 / 503 / 通信断 / タブを閉じた）。

**そして画面は成功したときと全く同じ反応を返す。** ボタンは「リクエストを受け取りました」に変わり、
アンケートの段も開く。**押した人にも、見ている運用側にも、失敗したことが伝わらない。**

### 実際に失敗する窓が存在した

`page` 列を足した T-058 のデプロイでは、**新しいブラウザ側コード（`{id, page}` を送る）と
古い受け口（`{id}` ちょうどしか受けない）が同時に存在する窓**があった。この窓で押した
ブラウザは 400 を受け取り、**それでも識別子だけは保存された。** そのブラウザは今も送らない。

**PO の手元のブラウザがこの状態である可能性が高い。** この画面は数日にわたり PO が
繰り返し押して確認しており、最初の1回はその窓に入りうる。

### 本番での実測（2026-09-08、オーケストレーター）

Chrome ヘッドレス + CDP で `https://pergram.site/ja/protein/` のボタンを実際に押し、
`/api/request-signal` への送信を**横取りして中止**した（本番 D1 に行を作らずに観測した）。

| 条件 | localStorage | 送信 | 画面の反応 |
| --- | --- | --- | --- |
| 初回訪問（識別子なし） | 押下後に付く | **`{"id":"e9ef…","page":"ja:protein"}` を送る** | 受領・段が開く |
| 再訪（識別子あり） | 変化なし | **一度も送らない** | **受領・段が開く（初回と同じ）** |

受け口の側は正常である（本番は HEAD と同じコードが動いている）。

| 送った本文 | 応答 |
| --- | --- |
| `{}` | 400 |
| `{"id":"<不正>","page":"ja:protein"}` | 400 |
| `{"id":"<正しいUUID>"}`（page 無し） | **400 — 新しい受け口が動いている証拠** |
| `{"id":…,"page":…,"extra":1}` | 400 |

CSP の `connect-src 'self'` も本番で確認済み。`/assets/request.js` は HEAD とバイト単位で一致。
**デプロイ漏れでも CSP でもない。ブラウザ側の状態機械の欠陥である。**

## 決定ログ

### 2026-09-08 「1ブラウザ1行」は保ったまま、確認が取れるまで同じ識別子を送り直す形にする
- 対象: 匿名シグナル / 押下の記録
- 決定: 識別子の保存は今までどおり送信の**前**に行う。そのうえで「サーバが受け取ったことを確認できたか」を別に持ち、確認が取れていない間は**同じ識別子で**送り直す。受け口は `INSERT OR IGNORE` なので、送り直しても行は増えない
- 却下案: 保存を送信の**後**にする → 応答が返らなかった回が次回に別の UUID で数え直され、同じブラウザが2人に見える（T-051 の 🔒 の理由そのもの）
- 却下案: 押すたびに送る → 同じブラウザが何行も作り、「何人が意思表示したか」が水増しされる
- 却下案: 失敗をユーザーへ見せて再試行させる → 保存は計測の都合であってユーザーの用ではない（T-051 の 🔒）
- 出典: セッション内のオーケストレーターの実測（本番、CDP で送信を横取り）、成果物なし

### 2026-09-08 受け入れテストの先行作成を実装担当に行わせる（T-058 と同じ扱い）
- 対象: 進め方
- 決定: 変更が「送信の可否の判定」に限定され判定基準がほぼ一意であるため、テスト担当の先行作成を省く。**付帯条件として RED の実出力の提示を必須にする**
- 却下案: 標準フロー（テスト → 実装）を回す → セッションコストが既に高く、判定基準が一意な変更に往復を掛ける利得が小さい。**同じ判断を T-058 で行い、実際に機能した**
- 出典: セッション内のオーケストレーターの判断、成果物なし

### 2026-09-08 受領の確認は別キー `pergram.request_signal_ack` に、確認の取れた識別子そのものを入れる
- 対象: 匿名シグナル / 押下の記録
- 決定: 既存の `pergram.request_signal_id` は**名前も意味も値も変えない**（送信の前に保存する識別子のまま）。
  受領の確認は別キーに置き、値は `1` のような印ではなく**確認の取れた識別子そのもの**を入れる。
  送信を止めるのは `id が在る かつ ack === id` のときだけ
- 却下案: 既存キーの値の形を変える（`"<uuid>:ok"` など）→ **既に識別子を持つブラウザが全滅する。**
  PO の手元のブラウザが救われることがこの修正の価値そのものであり、そこを壊す案は採れない
- 却下案: ack を `1` のような印にする → 識別子と紐付かないため、識別子が何らかの理由で
  振り替わったときに**古い確認が新しい識別子を黙らせる**。同じ欠陥が形を変えて戻る
- 出典: `src/assets/request.js` の `SIGNAL_ACK_STORAGE_KEY` 付近のコメント
