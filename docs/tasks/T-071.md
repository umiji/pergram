## 申し送り

1. **⛔ どのブランチへ push しても本番へ出る。**Cloudflare の Deploy command が `npx wrangler deploy` で、
   ブランチに関係なく本番の Worker を置き換える。**今日それを実測で確認した**
   （`org/request-survey` のコードが `pergram.site` で配信されている）。
   **したがって、移行が流れる前に push すると、`waitlist` への登録が全部壊れる**
   （`id` 列の無い表へ `id` を入れようとして失敗する）。**今は登録が動いているので、これは改悪になる。**
   **commit だけして push しないこと。push はオーケストレーターが移行の後に行う。**
2. **受け口 `/api/request-survey` のパスと本文の形を変えないこと。**
   T-070 で入れた「出荷箱」により、**503 で送れなかった回答が利用者のブラウザに控えられている。**
   パスか本文の形を変えると、その控えは永久に送れず、**回答が失われる。**
   保存先を `waitlist` へ変えるだけにする
3. **`request_survey` テーブルは本番に一度も存在していない**（`num_tables` は 3 のまま）。
   だから消すのは安全である。移行SQL ごと消す
4. **着手時点で `tests/hero_ranking.test.js` の2件が既に赤である**（T-049）。自分の失敗と読まないこと

## 決定ログ

### 2026-09-08 匿名のアンケート回答は waitlist へ相乗りさせる。email の主キーを外す
- 対象: アンケートの保存 / データ保護
- 決定: **`waitlist` を作り直し、`email` の PRIMARY KEY を外して匿名の行を入れられるようにする。**
  `request_survey` テーブルは作らない（本番に一度も存在していないので取り下げるだけでよい）
- 経緯: **PO の判断。**選択肢を提示したうえで選ばれた
- 却下案: `request_survey` を作る（T-070 の実装）→ **PO が「余計なテーブル追加しないでくれ」と却下**
- 付帯条件: SQLite は PRIMARY KEY を後から外せないため、**表の作り直し**（新表を作る→移す→消す→改名）になる。
  本番データを直接触るので、**移行の前に退避を取る**（取得済み: 4行）
- 上書き対象: T-070 2026-09-08（匿名のアンケート回答は新しいテーブルへ入れる。既存2つには列を足さない）
- 出典: セッション内の PO 判断

### 2026-09-08 匿名の識別子とメールアドレスを、同じ行に置かない
- 対象: データ保護 / アンケートの保存
- 決定: **1行が `id` と `email` を同時に持つことを、DB の CHECK 制約で禁じる。**
  匿名の行は `id` だけを持ち、メールを入れた人の行は `email` だけを持つ
- 理由: **`waitlist.id` に入る値は `request_signal.id` と同じ匿名の識別子である。**
  もし同じ行が `id` と `email` を両方持てば、**それまで匿名だったボタン押下の1行1行が、
  すべてメールアドレスへ紐づく。**`request_signal` が3列しか持たない理由
  （「個人を識別できるものを何も持たないことが、この行の存在理由である」）が丸ごと崩れる。
  **表を1つにするという PO の判断は、この線を越えることまでは含んでいない**
- 却下案: 制約を付けず運用で気をつける → **理由を知らない担当が将来必ず両方入れる。**
  DB が拒否する形にしておけば、間違えた時点で落ちる
- 却下案: メールを入れた時点で匿名の行に `email` を書き足して1行にまとめる →
  **まさにこの紐づけが起きる。**重複して2行残るほうがはるかに安全である
- 出典: `.claude/rules/pergram-compliance.md`「データ保護」、`worker/request_signal.js` 冒頭の 🔒
