## 決定ログ

### 2026-09-08 匿名のアンケート回答は waitlist へ相乗りさせる。email の主キーを外す
- 対象: アンケートの保存 / データ保護
- 決定: **`waitlist` を作り直し、`email` の PRIMARY KEY を外して匿名の行を入れられるようにする。**
  `request_survey` テーブルは作らない（本番に一度も存在していないので取り下げるだけでよい）
- 経緯: **PO の判断。**選択肢を提示したうえで選ばれた
- 却下案: `request_survey` を作る（T-070 の実装）→ **PO が「余計なテーブル追加しないでくれ」と却下**
- 付帯条件: SQLite は PRIMARY KEY を後から外せないため、**表の作り直し**（新表を作る→移す→消す→改名）になる。
  本番データを直接触るので、**移行の前に退避を取る**（取得済み: 4行）
- 上書き対象: T-070 2026-09-08（匿名のアンケート回答は新しいテーブルへ入れる。既存2つには列を足さない）
- 出典: セッション内の PO 判断

### 2026-09-08 匿名の識別子とメールアドレスを、同じ行に置かない
- 対象: データ保護 / アンケートの保存
- 決定: **1行が `id` と `email` を同時に持つことを、DB の CHECK 制約で禁じる。**
  匿名の行は `id` だけを持ち、メールを入れた人の行は `email` だけを持つ
- 理由: **`waitlist.id` に入る値は `request_signal.id` と同じ匿名の識別子である。**
  もし同じ行が `id` と `email` を両方持てば、**それまで匿名だったボタン押下の1行1行が、
  すべてメールアドレスへ紐づく。**`request_signal` が3列しか持たない理由
  （「個人を識別できるものを何も持たないことが、この行の存在理由である」）が丸ごと崩れる。
  **表を1つにするという PO の判断は、この線を越えることまでは含んでいない**
- 却下案: 制約を付けず運用で気をつける → **理由を知らない担当が将来必ず両方入れる。**
  DB が拒否する形にしておけば、間違えた時点で落ちる
- 却下案: メールを入れた時点で匿名の行に `email` を書き足して1行にまとめる →
  **まさにこの紐づけが起きる。**重複して2行残るほうがはるかに安全である
- 出典: `.claude/rules/pergram-compliance.md`「データ保護」、`worker/request_signal.js` 冒頭の 🔒

### 2026-09-08 受け口が書く列を「自分の鍵の列だけ」に固定した

- 対象: アンケートの保存 / waitlist の書き込み
- 決定: **`/api/waitlist` は `email` + 回答4 + 日時の6値だけを書き、`id` 列に触らない。
  `/api/request-survey` は `id` + 回答4 + 日時の6値だけを書き、`email` 列に触らない。**
  触らない列は NULL のまま残る
- 理由: **「もう一方の鍵を、うっかり空文字で埋める」経路をそもそも作らないため。**
  CHECK 制約は `id` と `email` が同時に非 NULL の行を止めるが、片方を空文字 `''` で
  埋める実装を書かれると制約は通ってしまい（空文字は NULL ではない）、
  **匿名の行にメールアドレスの列が生えたのと同じ状態**になる。書かなければ起きない
- 副次的な利点: どちらの受け口もバインドは6値のままなので、
  **`tests/worker.test.js` の `STORED_COLUMNS = 6` を書き換えずに済む。**
  失効していない検査を巻き添えで緩めない
- 却下案: 7列すべてを両方の受け口が書き、使わない側に NULL を明示的に入れる →
  上の空文字の事故と、列の追加のたびに2箇所を直す手間を招く
- 出典: セッション内のテスト設計。目印は `tests/request_survey.test.js` の
  「A-4 🔒 匿名の受け口の SQL は email 列に一切触らない」と定数 `BOUND_VALUES`

### 2026-09-08 CHECK 制約は「両方は持てない」までにとどめる

- 対象: データ保護 / waitlist の制約
- 決定: **`id` と `email` が同時に非 NULL の行だけを拒否する。**
  「どちらも無い行」は禁じない
- 理由: 禁止事項に書かれているのは「1行が `id` と `email` を同時に持ってはならない」であり、
  **書かれていない縛りをテストで足さない。** かつ、どちらも無い行はアプリからは作れない
  （`/api/waitlist` は不正なメールを 400、`/api/request-survey` は不正な UUID を 400 で捨てる）
- 却下案: 排他的論理和（ちょうど片方）を要求する → **実装が
  `CHECK (id IS NULL OR email IS NULL)` と書いた場合に、仕様上正しいのに落ちる。**
  完了条件 A-4 が求めているのは「両方持つ行を DB が拒否する」ことだけである
- 出典: `docs/tasks/T-071.md` の `## 禁止事項` と完了条件 A-4

### 2026-09-08 既存4行の生き残りは、退避ファイルではなく合成データで検査する

- 対象: 移行の検証
- 決定: 本番の退避（`<scratchpad>/waitlist_backup.sql`）を**テストから読まない。**
  代わりに**本番と同じ形の旧スキーマ（`email TEXT PRIMARY KEY` の6列）を `node:sqlite` に
  組み立て、合成した4行を入れ、`worker/migrations/` の新しい移行SQL を実際に流して**、
  `email` / 回答4種 / `created_at` が1文字も変わらないことを見る（完了条件 B-2）
- 理由: 退避ファイルは**本物のメールアドレスを含む**うえ、リポジトリの外にあるので
  他の環境でテストが走らない。**移行SQL そのものを実行して確かめる**ほうが、
  検査としても強い（同じ仕掛けで B-1「移行後の姿が schema.sql と一致」も見られる）
- 却下案: 退避ファイルをテストの入力にする → 個人情報がテスト環境へ広がる。
  ファイルが無い環境でテストが落ちる
- 付帯条件: 既に本番へ流れた移行SQL 3本はファイル名の集合（`SHIPPED_MIGRATIONS`）で
  除外する。**T-071 で足す分はその集合の外にある**という前提で新旧を見分けている
- 出典: `tests/request_survey.test.js` の `PRODUCTION_SCHEMA` / `EXISTING_ROWS` / `migrated()`
