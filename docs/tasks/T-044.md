### 2026-09-04 露出層リプの選定軸を min_faves から相手のフォロワー数（12万）へ移す
- 対象: X運用 / 露出の調達 / リプライ
- 決定: **露出層リプの相手を「min_faves:50 以上＝もう伸びた投稿」ではなく「フォロワー12万超のアカウント」で選ぶ。**
  相手は事前に人が確認した `watchlist` から取り、`(from:a OR from:b …) -filter:replies lang:ja` を
  最新タブで回す。**この式に `min_faves:` を付けない**（付けると投稿直後が必ず落ち、式の目的が消える）。
  watchlist の外を拾う保険として `min_faves:10` の発見式を残す。窓の探索式（`min_faves:200〜300`）は
  目的が違う（観客が既に集まっている話題を探す）ので高い閾値のまま維持する。
- 根拠（一次情報 / `xai-org/x-algorithm` commit `9b0dc31` 2026-09-04）:
  1. `home-mixer/filters/oon_retweet_reply_filter.rs` — **フォローされていない相手のリプライは
     採点前に候補から捨てられる。**リプの表示回数は「元投稿のリプ欄を開いた人の数」でほぼ決まる
  2. `grox/flows/reply_spam/task_filter.py` — `FOLLOWER_COUNT_THRESHOLD_FOR_REPLY_RANKING = 120000`。
     **Grok によるリプの採点が走るのは、元投稿または親の著者が12万フォロワーを超えるときだけ。**
     12万以下は `low_blast_radius` としてスキップされ、代わりにスパム判定（`TaskSpamFilter`）が走る
- 却下案:
  - `min_faves:` の値を 50→10 へ下げるだけ → **`min_faves` は「相手の大きさ × 経過時間」の積でしか
    動かない。**値をいくつにしても「大きいアカウントの、リプ欄が空いている投稿」だけは取り出せない
  - `min_faves:` を捨てて素の検索語だけにする → config.yaml の実測どおり、まだ伸びていない小さい
    投稿ばかり返る。それは意図層であって露出層ではない
  - `since_time:` で直近30分を切る → **この演算子を実測していない。**未実測の演算子を日次運用の
    中心に置かない
- 付帯条件: **`from:` も未実測である。** 着手の最初に1回だけ手で効くことを確かめる（§9-11）。
  watchlist へ入れるのは判定の境目12万に余裕を持たせて**15万以上**にする（§9-12）。
- 上書き対象: T-031 2026-09-03（`X運用 / 露出の調達` のうち、露出層リプの探し方を定めた部分）
- 出典: `docs/Marketing/X_algorithm_findings.md` §3.3 / §3.4、`docs/Marketing/X_growth_design.md` §2.2 / §4.3

### 2026-09-04 エンゲージメントの重みを一次情報の実数へ置き換える
- 対象: X運用 / 投稿の型 / 型の効果測定
- 決定: 二次情報の「会話150倍・リプ27倍・RT20倍・ブックマーク10倍」を**採らない。**
  一次情報の本番既定値（`home-mixer/params/param.rs`）を使う —
  `share_via_copy_link` 20.0 / `reply` 5.0（相互フォロー時 +15.0 で 20.0）/ `quote` 5.0 /
  `follow_author` 4.0 / `retweet` 1.0 / `favorite` 0.5 / **`profile_click` 0.0** /
  **ブックマークは重み自体が存在しない**。
  重みは**予測確率に掛かる**のであって行動回数に掛かるのではないため、
  「リプ1件＝いいね10件」という換算は成立しない。
- 却下案: 二次情報のまま採る → **出所を追跡したところ 2023年版リポジトリのコミュニティ推計だった。**
  2023年版の公開されている `default` は全部 0.0 で、コードからは読めない数字である。3年ぶんの更新を
  挟んでいない
- 付帯条件: **プロフィールクリックは指標として残す。** 重み 0.0 で無効になったのは「押されれば次の
  露出が増える」という因果だけで、**流入の導線としては依然として正しい**（§2.2b）。
  §2.4 の見積りと §6.6 の判定指標は変更しない
- 出典: `docs/Marketing/X_algorithm_findings.md` §1、`docs/Marketing/X_growth_design.md` §2.2b / §5.4

### 2026-09-04 一次情報で裏が取れなかった論点は、根拠として使わない
- 対象: X運用 / 露出の調達 / 計測
- 決定: 次の論点は「一次情報で裏が取れなかった」と明示し、**設計の根拠に使わない。**
  「最初の30〜60分の初速が配信量を決める」／「ツリー3〜5本が +40〜60%」／
  「リプ欄で早い順が有利」／「シャドウバンの数値の閾値」／「500フォロワー50リプ > 1万フォロワー20いいね」。
  代わりに一次情報にあった時間の窓を使う — **新規著者ブーストは投稿から24時間、ホーム表示1,000未満**
  （`ColdStartMaxPostAgeSecs = 86400` / `ColdStartImpressionThreshold = 1000`）。

- 却下案: 二次情報のまま「30分で決まる」を採る → **二次情報の側が自ら
  `Source: Industry consensus`（業界の通説）と注記しており、コード由来だと主張していない**
- 付帯条件: §4.2 の「1日12件を超えない」は**根拠が無いまま置いた安全弁である**と明記した。
  一次情報が代わりに教えたのは、件数より**文面の重複**のほうが直接の危険だということ
  （日本語には `bbq_duplicate_text_characters_replies_cjk` という文字単位の専用ジョブがある）
