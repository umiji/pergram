## 申し送り

**オーケストレーターが 2026-09-03 に速報として調べた範囲。出発点として使ってよいが、
すべて二次情報であり、あなたが裏を取ること。**

| 論点 | 速報で得た内容 |
|---|---|
| エンゲージメントの重み | 会話（返信→著者が返信）**150倍** / リポスト20倍 / リプライ27倍 / ブックマーク**10倍**（対いいね） |
| 初速 | **最初の30〜60分**のエンゲージメント速度が配信量を大きく左右する |

**🔴 最も重い疑い**: T-031 §2.2 / §4.3 は露出層リプの相手を **`min_faves:50` 以上**、つまり
**既に伸びた投稿**から探せと書いている。**しかし上記が正しいなら、狙うべきは「これから伸びる投稿の、
リプ欄がまだ空いている最初の30〜60分」であり、既に伸びた投稿はリプ欄が埋まった後である。**
**設計が逆を向いている可能性がある。これを最優先で判定すること。**

**ただし `config.yaml` に実測済みの制約がある** — X の検索演算子に `min_impressions:` は存在せず、
最新タブに素の検索語だけを渡すと**まだ伸びていない投稿ばかりが返る**。
「投稿直後を狙う」設計に切り替えるなら、**その相手をどう機械で見つけるかまで書くこと。**
「早く見つけろ」だけでは実行できない。

**PO 確認済み（2026-09-03）**: 手作業は1日60〜90分。Day1 = 2026-09-03、Day7ゲート 9/9、終端 9/16。
**この調査が効くのは Day2 以降である。** 9/3 の投稿2本は Buffer に登録済みで動かせない。

**Buffer の API はツリーと画像に対応している**（2026-09-03 に確認）。
`TwitterPostMetadataInput.thread: [ThreadedPostInput!]` / `ThreadedPostInput.assets: [AssetInput!]!`。
**ツリーの本数を増やす提案は、実装可能である**（T-037 で実装する）。
