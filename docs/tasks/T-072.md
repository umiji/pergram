## 目的

**PO 指摘（2026-09-09）:**

> 同じセッションで成分アンケートの内容を送ったあとにメールアドレスを送ったらレコード2つに
> 分かれるのは流石にだめでしょ。同じ人がアンケートとメールアドレス回答してんのに
> レコード分かれるのがOKなわけなくない？

**指摘は正しい。T-071 の設計判断（オーケストレーター）が誤っていた。**

いまこうなっている。

| 利用者の行動 | 書かれる行 |
| --- | --- |
| アンケートに答えて送信 | `waitlist` に1行（`id` のみ / **回答4項目**） |
| 続けてメールアドレスを登録 | `waitlist` に**もう1行**（`email` のみ / **同じ回答4項目**） |

**2行に分かれるだけでなく、同じ回答が両方の行に入る。**`worker/waitlist.js` も回答4項目を書くためである。
つまり「クレアチンを見たい人」を数えると**同じ人を2回数える**。
**`docs/research/validation-plan.md` の判定に直接効く。**次に何を作るかの判断を誤る。

## 何を読み違えたのか — 次の担当が同じ結論に戻らないために

分けた理由は「`waitlist.id` と `email` が同じ行に載ると、`request_signal` の匿名の押下が
すべてメールアドレスへ紐づく」ことだった。**この懸念自体は正しい。**
🔒 **紐づけてよいという話には、この修正でもならない。**

**誤っていたのは「だから行を分ける」という結論のほうである。両立する形が在った。**

> **メールアドレスが送られた時点で、匿名の行に `email` を書き込み、同時に `id` を捨てる。**

- 行は**1つ**になる。回答は最初に答えたものが残る
- 残るのは `email` だけ。**`id` は消えるので、`request_signal` と突き合わせる鍵はどこにも保存されない**
- `CHECK (id IS NULL OR email IS NULL)` はそのまま効く（`id` を消してから `email` を入れる順序になるため）

**T-071 には「両立しないと判断したら止めて報告」という停止条件（S-7）が置いてあった。
両立する形を探しきらずに2行で確定させたのは、オーケストレーターの判断ミスである。**

## 決定ログ

### 2026-09-09 まとめ方は「匿名の行を消してから、メールアドレスの行へ書く」

- 対象: アンケートの保存 / waitlist の受け口
- 決定: `/api/waitlist` は、識別子付きの送信を受けたら
  (1) 匿名の行を `SELECT` して回答と `created_at` を引き取り、
  (2) `DELETE FROM waitlist WHERE id = ?` と既存の `INSERT … ON CONFLICT(email)` を
  **`env.DB.batch()` の1トランザクションで**流す。**`id` 列へは一切書かない。**
- 却下案: `UPDATE waitlist SET email = ?, id = NULL WHERE id = ?` の1文で済ませる →
  **先にメールアドレスだけ登録していた人**（`email` の行が既にある）で
  `email TEXT UNIQUE` に当たって落ちる。回答の突き合わせも別途要る。
  この経路は受け入れテストに無かったので `tests/waitlist_merge_unit.test.js` で固定した
- 却下案: `DELETE` と `INSERT` を逐次で流す → 消せたのに書けなかった回で回答が消える。
  D1 の `batch()` は1トランザクションなので、原子性が無料で手に入る
- 付帯条件: **順序を入れ替えないこと。**「書いてから消す」にすると上の UNIQUE 衝突が戻る
- 出典: `worker/waitlist.js`（`handleWaitlist` の `if (carried)` 節のコメント）

### 2026-09-09 送信本文に載せる識別子のキー名は `signal_id`。保存列の `id` と同じ名前にしない

- 対象: アンケートの保存 / waitlist の受け口
- 決定: メールの段が添える匿名の識別子は、本文では **`signal_id`** という名前で運ぶ
  （`worker/waitlist.js` の `SIGNAL_ID_KEY`）。保存列 `id` とは別の名前にする
- 却下案: 本文でも `id` にする（保存列と同じ名前）→ **受け取った値をそのまま `id` 列へ
  入れる実装へ自然に手が伸びる。** その瞬間に匿名の押下がすべてメールアドレスへ紐づく。
  名前が違うことが「これは保存する値ではない」という手掛かりになる
- 🔒 **「保存列と揃っていないから」と `id` へ改名しないこと。** 揃っていないのが目的である
- 出典: `worker/waitlist.js` の `SIGNAL_ID_KEY` のコメント / `src/assets/request.js`

### 2026-09-09 まとめるときの回答は「送られてきた値が空なら、匿名の行の回答で埋める」

- 対象: アンケートの保存 / waitlist の受け口
- 決定: 引き取った回答は**既定値として**使う。送信本文に回答があればそちらを採り、
  空のときだけ匿名の行の値を入れる。`created_at` だけは**引き取った行の値をそのまま使う**
  （最初に答えた日時を後ろへずらさない。`worker/request_survey.js` と同じ理由）
- 経緯: T-072 本文の「回答は最初に答えたものが残る」は**回答が失われないこと**を
  言っており、優先順位の指定ではない。既存の `ON CONFLICT` の向き
  （「送られてきた値が空なら、今ある値を残す」）と揃えた
- 却下案: 匿名の行の回答を常に優先する → 同じ送信で回答を後から書き換えられなくなる。
  既存の上書き規則と向きが逆になり、経路によって挙動が変わる
- 出典: `worker/waitlist.js` / `tests/waitlist_merge.test.js` の A-2 群

### 2026-09-09 既にできている重複行を統合する SQL は書かない

- 対象: アンケートの保存 / 本番データ
- 決定: 本番に既にできている重複行（同じ人の匿名の行とメールの行）を統合する SQL は、
  このタスクでは**書かない。**修正は今後の登録にだけ効く
- 経緯: `## 判断してよい範囲` に「書くか」が入っていたので、書かない側を選んだ
- 却下案: 統合 SQL を用意して PO に流してもらう → **既存データを消す操作であり
  （共通の停止条件 S-2）、実装担当は `npx wrangler d1 execute` が deny のため
  検証できない。** 検証していない破壊的な SQL を本番へ渡すことになる。
  「どの匿名の行がどのメールの人か」を後から突き合わせる鍵は
  **設計上どこにも保存されていない**ので、機械的に安全な統合はそもそも書けない
  （突き合わせられるなら、それ自体が匿名性を壊している）
- 付帯条件: **必要なら別タスクとして起票し、突き合わせ方を PO 判断で決めること。**
  件数の把握（`SELECT` だけ）なら破壊的でないので先に切り出せる
- 出典: セッション内の判断、成果物なし

### 2026-09-09 匿名の行の照会が失敗しても、メールアドレスの登録は 200 で通す

- 対象: アンケートの保存 / waitlist の受け口
- 決定: 引き取る行の `SELECT` が落ちたら、ログだけ残して**まとめずに登録を続ける**
  （`findAnonymousRow` が例外を握って null を返す）。行が2つ残るのは劣化として許す
- 却下案: 書き込みと同じく 503 を返す → **まとめは記録の都合、登録は利用者の用である。**
  記録の都合で利用者が待機リストに載れなくなるほうが害が大きい
- 🔒 **「一貫性がないから」と 503 へ揃えないこと。** 意図的に非対称にしてある
- 出典: `worker/waitlist.js` の `findAnonymousRow` / `tests/waitlist_merge_unit.test.js`

### 2026-09-09 匿名の行とメールの行は1行へまとめる。まとめる時に匿名の識別子を捨てる
- 対象: アンケートの保存 / データ保護
- 決定: メールアドレスが送られた時点で、**匿名の行へ `email` を書き込み、同時に `id` を捨てる。**
  行は1つになり、保存されるのは `email` だけになる
- 経緯: **PO 指摘。**T-071 の「2行に分かれる」設計が、同じ人の回答を二重に数える
- 却下案: 2行のまま残す（T-071 の設計）→ **同じ回答が両方の行に入り、集計の分母が壊れる。**
  `docs/research/validation-plan.md` の判定に直接効く
- 却下案: CHECK を外して `id` と `email` を同居させる → **`request_signal` の匿名の押下が
  すべてメールアドレスへ紐づく。**`request_signal` が3列しか持たない理由が丸ごと崩れる
- 上書き対象: T-071 2026-09-08（匿名の識別子とメールアドレスを、同じ行に置かない）
  ⚠️ **「同じ行に置かない」という結論そのものは生きている。**失効するのは
  「だから行を2つに分ける」という部分だけである
- 出典: セッション内の PO 指摘

### 2026-09-09 受け入れテストは、識別子を載せるキーの名前を決め打ちしない
- 対象: アンケートの保存 / 受け入れテスト
- 決定: `tests/waitlist_merge.test.js` は、**ブラウザ（`src/assets/request.js`）を1度走らせて、
  匿名の識別子の値が載っているキーを見つけてから**（`IDENTIFIER_KEY`）サーバ側の検査に使う。
  キー名をテスト側で固定しない。見つからない間（未実装の間）は `id` を仮に使う
- 経緯: T-072 `## 判断してよい範囲` に「匿名の識別子を `/api/waitlist` の本文へどう載せるか」が
  入っている。テストがキー名を決め打ちすると、**完了条件ではなく実装手段のほうを縛る**ことになる
- 却下案: 本文のキーを `id` に固定する → 実装が `signal_id` などを選んだ瞬間に、
  正しい実装が受け入れテストで落ちる（偽の Blocker）
- ⚠️ **この仕掛けを「回りくどいから」と定数へ畳まないこと。** 畳むと上の縛りが戻る
- 出典: tests/waitlist_merge.test.js の `detectIdentifierKey()`

### 2026-09-09 「待機リストへ送る本文に id を混ぜない」検査を2件、緩めた
- 対象: アンケートの保存 / 受け入れテスト
- 決定: `tests/request_survey.test.js`（A-2 メールアドレスの段…）と
  `tests/request_flow_behavior.test.js`（🔒 送信本文は保存してよい列の範囲だけ）の
  **キー集合の検査を、「匿名の識別子だけは載ってよい」形へ緩めた。**
  保存列の外の項目（年齢・体調など）を弾く役目はそのまま残してある
- 経緯: この2件は T-071 の「行を2つに分ける」設計を前提に書かれており、**その前提が
  T-072 の PO 指摘で失効した。** 残すと、正しい実装が既存テストで落ちる。
  実装担当がテストを書き換える形になるのを避け、テスト担当の側で先に直した
- 却下案: そのまま残して実装担当に任せる → 「落ちているテストを通すためにテストを書き換える」
  形になり、規約上も判別がつかなくなる
- 却下案: 検査ごと削除する → 保存列の外の項目を送らせない見張りまで失う
- 🔒 **守るべき線は変わっていない。「`id` と `email` を同じ行に保存しない」である。**

  **「🔒 が消えている」と見て元へ戻さないこと**
- 上書き対象: T-071 2026-09-08（匿名の識別子とメールアドレスを、同じ行に置かない）のうち、
