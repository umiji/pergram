## 目的

**PO 指摘（2026-09-09）:**

> 同じセッションで成分アンケートの内容を送ったあとにメールアドレスを送ったらレコード2つに
> 分かれるのは流石にだめでしょ。同じ人がアンケートとメールアドレス回答してんのに
> レコード分かれるのがOKなわけなくない？

**指摘は正しい。T-071 の設計判断（オーケストレーター）が誤っていた。**

いまこうなっている。

| 利用者の行動 | 書かれる行 |
| --- | --- |
| アンケートに答えて送信 | `waitlist` に1行（`id` のみ / **回答4項目**） |
| 続けてメールアドレスを登録 | `waitlist` に**もう1行**（`email` のみ / **同じ回答4項目**） |

**2行に分かれるだけでなく、同じ回答が両方の行に入る。**`worker/waitlist.js` も回答4項目を書くためである。
つまり「クレアチンを見たい人」を数えると**同じ人を2回数える**。
**`docs/research/validation-plan.md` の判定に直接効く。**次に何を作るかの判断を誤る。

## 何を読み違えたのか — 次の担当が同じ結論に戻らないために

分けた理由は「`waitlist.id` と `email` が同じ行に載ると、`request_signal` の匿名の押下が
すべてメールアドレスへ紐づく」ことだった。**この懸念自体は正しい。**
🔒 **紐づけてよいという話には、この修正でもならない。**

**誤っていたのは「だから行を分ける」という結論のほうである。両立する形が在った。**

> **メールアドレスが送られた時点で、匿名の行に `email` を書き込み、同時に `id` を捨てる。**

- 行は**1つ**になる。回答は最初に答えたものが残る
- 残るのは `email` だけ。**`id` は消えるので、`request_signal` と突き合わせる鍵はどこにも保存されない**
- `CHECK (id IS NULL OR email IS NULL)` はそのまま効く（`id` を消してから `email` を入れる順序になるため）

**T-071 には「両立しないと判断したら止めて報告」という停止条件（S-7）が置いてあった。
両立する形を探しきらずに2行で確定させたのは、オーケストレーターの判断ミスである。**

## 変更範囲

- `worker/waitlist.js` — 匿名の行を引き取って1行へまとめる
- `src/assets/request.js` — メールの段の送信に、そのブラウザの匿名の識別子を添える
- `tests/` — 受け入れテストと単体テスト
- `.claude/rules/pergram-compliance.md` — 「データ保護」の記述の更新（**まとめる時に `id` を捨てること**）

## 禁止事項

- 🔒 **`id` と `email` を同じ行に保存しない。CHECK 制約を外さない。**
  まとめるときは**必ず `id` を捨てる**。「1行にするために CHECK を外す」は解ではない
- 🔒 **`request_signal` の3列に手を触れない**
- 🔒 IP・User-Agent・リファラ・ページ内の位置を保存しない
- **移行SQL を書かない。**テーブルの形は T-071 のままで足りる
- **既存の回答を消さない。**まとめるときに、匿名の行の回答が失われないこと
- 自由記述の中身を解釈して弾かない。サーバがやるのは長さで切ることだけ
- 帯の見た目（T-061 で確定）を触らない
