## 目的
「X 向けに pergram アカウントの投稿を AI で量産する」という要求に対し、
**現状の `.media-agent` 機構が構造的に何をできず、何が欠けているか**を技術の側から洗い出し、
対策を設計する。

既に判明している深刻な事実が2つある。

1. **手書き本文を投稿候補として登録する口が無い。** `media-agent post` / `run` は必ず AI が
   本文を生成する。9/3 の下書きは `BufferConnector` を直接呼ぶスクリプトで入れており、
   **PolicyEngine（承認キュー・1日2本の上限・重複判定）を通っていない**
2. **Buffer 経由で投稿したものが media-agent の DB に紐づいているか不明。**
   紐づいていなければ `media-agent report` の playbook 別集計は空のままで、
   X_kgi_2weeks.md §9 が前提にしている「型別の効果測定」が成立しない

これを飛ばすと、投稿設計（T-031）だけを立派にしても、**流し込む経路と測る経路が無い**まま
14日が終わる。

## 完了条件
`docs/Marketing/media-agent-gap-analysis.md` が存在し、以下の6点をすべて含むこと。

1. **機構の現況マップ**: 収集 → 生成 → 評価 → 承認 → 配信 → 計測 の各段が、いま
   何によって実行され、どこで人手に落ちているか。**実行して確認した出力を根拠として添える**
2. **課題の一覧**: 1件ごとに「事象 / 根拠（ファイル・行・コマンド出力）/ KGI への影響 /
   深刻度（Blocker / Major / Minor）」。**根拠のない推測は「未確認」と明示する**。
   最低限、次の論点は判定して載せること:
   - 手書き本文を正規の経路へ入れる口が無いこと（PolicyEngine を迂回している）
   - Buffer 経由の配信と media-agent の Post レコードが紐づくか。
     紐づかないなら `report` の playbook 別集計は成立するのか
   - `x metrics` が拾う指標と、Buffer で配信した投稿が対応づくか
   - 画像添付の経路があるか（型は「1枚目に比較画面の画像」を前提にしている）
   - ツリー投稿の扱い（Buffer が単発投稿しか作れない件）
   - 生成文の文字数制御（X の CJK 重み付き 280。playbook の例文2本が既に超過している）
   - strategy.md / playbooks に**数字がハードコードされ、実データと食い違っている**問題
     （含有率「60%〜90%・1.5倍」は誤り。正しくは 33%〜93.6%・2.8倍）
   - 禁止語・禁止事項が生成物で実際に守られているかの検査の有無
   - リプライ（T1/T2）の候補生成を支援する口があるか
3. **対策**: 課題ごとに、対策・想定工数（S/M/L）・変更が及ぶ範囲・副作用。
   **`media-agent` 本体（`~/.local/bin/media-agent`、このリポジトリ外）を変更する対策と、
   このリポジトリ内で閉じる対策を必ず区別する**
4. **最小構成の提案**: 14日で KGI を追う前提で、**Day1〜Day3 のうちに入れるべき最小の手当て**は
   どれか。優先順位と、その順にする理由
5. **やらない方がよいことの明示**: 自動化すると凍結・規約違反・法令違反のリスクが上がるもの
6. **タスク化の素案**: 対策を、このリポジトリのタスク台帳に登録できる粒度へ割った一覧
   （タスク名 / 目的1行 / 完了条件の案 / 依存）。**CSV には書かない。文書の中に一覧として置く**

## 決定ログ

### 2026-09-03 14日間は、測定の正典を media-agent の DB ではなくリポジトリ内の投稿台帳に置く
- 対象: X運用 / 計測
- 決定: 14日間（〜2026-09-16）に限り、型別の効果測定の正典を `media-agent` の SQLite（`post` / `performance`）ではなく、
  **このリポジトリ内に置く「投稿台帳」と Buffer の送信済み指標**に置く。`media-agent report` はこの期間使わない。
  `media-agent` は生成の相談相手と X の観測（`x search` / `x learn`）としてのみ使う。
- 却下案:
  (A) `media-agent.db` の `post` テーブルへ直接 INSERT して `report` を成立させる → 他プロジェクトが所有する
      schema v5 へ外から書くことになり、本体の更新で壊れる。**壊れても例外が出ず「測れているつもり」になる**
  (B) `policy.actions.post.mode` を `auto` にして `run` を回す → 承認と禁止表現検査の砦が同時に外れる（N-02）
  (C) 本体（`media-agent-bmad`）に本文投入口と承認の出口を実装してから運用を始める → Day1 が今日であり、
      改修完了まで配信が止まる。**Day14 以降の宿題として残す**
  (D) Buffer をやめて X API を直接使う → 従量課金（URL 入り投稿 1 件 $0.200）と工数が回収できない
  (E) 正典を media-agent の DB 側に置いたまま寄せる → (A) か (C) が必要で、両方却下された以上不可能
- 付帯条件: Day14 以降に本体側へ本文投入口と承認の出口が入った時点で、正典を戻すかを再判断する
- 出典: `docs/Marketing/media-agent-gap-analysis.md` §7

### 2026-09-03 rules.md の「禁止表現」節が箇条書きであることは、体裁ではなく機能上の要件である
- 対象: X運用 / 法令順守
- 決定: `.media-agent/x/pergram-jp/rules.md` の「## 禁止表現」節は、**必ず `- ` で始まる箇条書きにする。**
  素の行の羅列に戻してはならない。
- 却下案: 現状のまま（素の行の羅列）にしておき、禁止語の判定は LLM に任せる → `core/rules.py` の
  `BrandRules.parse` は箇条書きの行しか拾わないため、13語が 1 語も検査に使われない。実測で
  「効果」「中身がスカスカ」「高品質」「あなたは不足しています」がすべて `violation()` = None を返した。
  **薬機法・景表法に対する機械的な砦がゼロになる**
- 出典: `docs/Marketing/media-agent-gap-analysis.md` G-05 / `media-agent-bmad/src/media_agent/core/rules.py`

### 2026-09-03 深刻度の判定基準を「14日の経路が成立するか」で切った

  Minor = 手間が増える、で判定する。実装の美しさや設計上の負債は深刻度に反映しない。
- 却下案: 一般的な重大度（機能停止 / 機能低下 / 軽微）で切る → `report` が空であることは機能停止ではないが、
