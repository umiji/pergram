## 目的

**T-058 で PO 判断により上書きされた不変条件が、2箇所に古いまま生き残っている。
加えて、本番デプロイの順序の危険が運用手順書へ渡っていない。**

**1. 上書きされた 🔒 が4つ目のファイルに残っている（R-058-1 / Major）**

`worker/index.js:16` のルート表のコメントが
`// 要望の第1段階を匿名の1行として残す（T-051）。持つのは UUID と日時だけ` のまま。

T-058 の完了条件9は書き換え対象を**3ファイル名指し**で列挙したため、
正しく実装しても4つ目が取り残された。**この組織は会話履歴を継承しないので、
次に触る担当がこの1行を根拠に `page` 列を「規約違反」として削れる**
—— 完了条件9が防ごうとした事象そのものである。

**2. デプロイ手順書に移行SQLが載っていない（R-058-2 / Major）**

`docs/ops/deploy.md` の §3 が「`waitlist` と `price_alert` ができる」と書いており、
**`request_signal` が漏れている**（T-051 以来）。移行SQLの実行例も
`2026-08-10_waitlist_freetext.sql` の1本だけで、`2026-09-07_request_signal.sql` と
`2026-09-08_request_signal_page.sql` が**どちらも載っていない**。`README.md` にも記載なし。

さらに **T-058 自身が見つけた「①移行SQL → ②デプロイ の順を逆にすると、
押下の INSERT が列不足で失敗し要望ボタンが全て 503 で死ぬ」という危険が、
手順書の側に一切書かれていない。**

**本番への適用は 2026-09-08 に完了しているので当座の実害は無い。**
踏むのは**新しい D1 を作り直す場面**（ステージング、災害復旧）である。
危険の記録がタスクファイルにしか無いと、タスクが完了した時点で運用者から見えなくなる。

**3. 移行SQLの2回目が必ず失敗する旨が書かれていない（R-058-3 / Minor）**

`worker/migrations/2026-09-08_request_signal_page.sql` は、2回目の実行が
`duplicate column name` で必ず失敗する（SQLite に `ADD COLUMN IF NOT EXISTS` が無い）。
**実際に PO が本番で踏んだ。** `-- 1度だけ流す` はあるが「2度目のエラーは正しい挙動」
とは読めない。

**4. 規約の price_alert の記述が実態と違う（R-058-4 / Minor）**

`.claude/rules/pergram-compliance.md` の「価格アラートの**監視製品ID のみ**」が実態と違う。
`worker/schema.sql` の `price_alert` は `email` / `threshold_type` / `threshold_value` /
`created_at` も持つ。**T-051 以前からの誤りで、T-058 が悪化させたものではない。**
`price_alert` を書く経路は現在存在しない（`ROUTES` は2本だけ）ので法令上の実害も無い。
