## 目的

T-050 で製品一覧に要望の導線を置いたが、**PO がプレビューを見て 4 つの食い違いを指摘した。**

1. **製品一覧に、意思表示の入口が2つ並んでいる。** 「リリース通知を受け取る」（メール = 重い対価）と
   「他の成分・製品の追加をリクエスト」（1クリック = 軽い対価）が同じ場所に出ており、
   **T-050 が下げようとした対価を、隣のボタンが元に戻している。**
2. **同じ意思表示を指す言葉が、画面ごとに違う。** LP は「Waitlist」「リリース通知」、製品一覧は
   「リクエスト」。押した先が同じ導線であることが読み手に伝わらない。
3. **要望のセクションが、絞り込み・表示切替のツールバーより後ろにある。** 操作の道具より後ろに
   置くと、絞り込みを触りに来た人の視線の外へ落ちる。
4. **LP はいまも「メールアドレスを先に出せ」という形のまま。** 製品一覧だけを軽くしても、
   広告の着地点である LP が重いままなら、下げた対価は届かない。

加えて **PO が新しい要件を出した**: 第1段階の押下を、GA4 のイベントだけでなく
**D1 にも1行残す**（日付と UUID）。GA4 は CSP で全滅した実績があり（T-047）、
**計測が自分の手の中に無いと、また同じ理由で 0 件の意味が読めなくなる。**

## 禁止事項

- 🔒 **既存の `waitlist` テーブルの構造を変えない。** `email` が主キーであり、SQLite では後から
  変えられない。匿名の行は**別テーブル**に入れる。既存データの移行・削除は行わない（S-2）。
- 🔒 **匿名シグナルのテーブルに、UUID と日時以外の列を作らない。** IP・User-Agent・リファラ・
  成分・自由記述を入れない。**個人を識別できるものを何も持たないことが、この行の存在理由である。**
- 🔒 押下数・登録数を画面に描画しない（景表法の「人気」表示・N-03）。
- 🔒 リクエストの数を並び順に使わない。並び順は常に有効成分1単位あたりの価格。
- 🔒 自由記述の**本文**を GA4 へ送らない。書かれたかどうか（0 / 1）だけ。
- 🔒 自由記述には `lp.form.freeTextNote` の注記を必ず添える。離さない（N-01 / N-05）。
- 🔒 支援ウィジェットは1ページに1つ。
- 🔒 成分の効能・効果に触れる文章を新しく書かない（N-02）。文言は locales の固定文だけ。
- 🔒 **T-050 の決定ログのうち、PO 判断の3件を覆さない**（ヒーローのサンプル表記／意思表示は
  サービス単位で問う／LP からβ版へのリンクを消さない）。
- 落ちているテストを、テストや期待値の書き換えで通さない。

3. LP・製品一覧のヘッダの CTA の文言が、どちらも **`機能追加リクエスト`**

4. 製品一覧の HTML で、`data-request-cta` を持つ最初の要素の出現位置が
   `class="toolbar"` の出現位置**より前**である
5. LP に第1段階のボタン（`data-request-cta`）と、`data-request-step="survey"` /
   `"email"` / `"support"` の3段がこの文書順で存在し、**3段とも初期状態は `hidden`**
6. LP の旧・メールアドレス先行フォーム（`waitlist--step1`）が出力されない
7. 第1段階の押下で `POST /api/request-signal` が飛び、本文が `{"id":"<UUID>"}` のみである
8. 同一ブラウザの2回目以降の押下では POST しない（`localStorage` の
   `pergram.request_signal_id` が既にあれば送らない）。段は開く
9. `worker/schema.sql` に `request_signal` テーブルがあり、列は `id TEXT PRIMARY KEY` と
   `created_at TEXT NOT NULL` の**2つだけ**。同じ内容の移行 SQL が `worker/migrations/` にある
10. `POST /api/request-signal` が、UUID の形式でない `id`、`id` 以外のキー、本文なしを **400** で返す
11. `npm test` が全件 pass（`node --test tests/*.test.js`）
12. `npm run build` が成功する

## 申し送り

**PO が本セッションで確定した4点（2026-09-07）:**

1. **匿名シグナルは LP・製品一覧の両方で保存する。** 同じ意味の意思表示を2箇所で
   数え方を変えない。押された場所の区別は GA4 の `location` が持つ
2. **重複はブラウザごとに1件へ抑える。** 「何人が意思表示したか」に近い数字にするため。
   ブラウザを変えれば別人として数えられることは承知のうえ
3. **LP の既存のメールアドレス先行フォームは、段構造へ完全に置き換える**（併存させない）
4. **これは T-050 の決定「第1段階の計測は GA4 のイベントだけで行う／サーバに列を足さない」を
   上書きする PO 判断である。** 実装担当は元の決定を根拠に差し戻さないこと。
   ただし**既存の `waitlist` テーブルには一切触れない**という条件が付いている

**技術的な事実（調査済み）:**
- `waitlist` テーブルは `email` が主キー。**メールアドレス無しの行は物理的に入らない。**
  だから別テーブルにする
- 製品一覧の第1段階は現在サーバへ何も送っていない（GA4 のイベントのみ）
- `src/assets/request.js` は `[data-request-flow]` と `[data-request-cta]` が両方無いと
  早期 return する。LP で動かすには LP 側にも同じ目印が要る
- `src/assets/products.js` は絞り込み／リストが無いと早期 return する。
  **要望の操作をそちらへ統合してはならない**（T-050 の決定ログ）
