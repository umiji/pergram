## 目的

**組織の時短対策（D-001）の効果を測る道具が、単位を間違えている。**

会話記録（JSONL）は、**モデルの1回の応答を複数行に分けて書く**（文・思考・道具呼び出しが別の行になる）。
集計スクリプトはその行を1行ずつ数えているため、次の2つが同時に狂っている。

| 何が | どれだけ | 実測の根拠 |
| --- | --- | --- |
| `返答回数` 列 | **実 API 往復の約1.9倍** | 担当エージェントの記録72本で、usage を持つ行 6091 に対し requestId は 3128（比 1.95） |
| **トークン数そのもの** | **約1.87倍の過大計上** | 同 72本で、素の合計 **871,773,938** に対し束ね後 **466,489,431** |

**トークンの過大計上は、2026-09-13 の引き継ぎ記録にも載っていない新しい発見である**
（引き継ぎ記録は「`返答回数` が1.8倍」までしか書いていない）。同じ requestId の各行は
`input_tokens` / `cache_read_input_tokens` / `cache_creation` を**まったく同じ値で持っており**、
合算するとその回数ぶん重複する。`output_tokens` だけが行を追うごとに伸び、**最後の行が完全な値**になる。

これを直さないと、**折込の前後比較で1.9倍ずれた数字を基準値と突き合わせることになり、対策が失敗したように見える。**
また `docs/token-usage-pergram.csv` が示す全体量（約23.5億トークン）も、実際の倍近い値を出している。

あわせて、**このスクリプトには一度もテストが無い。** 「返答回数は往復ではなかった」という誤りが
長く気づかれずに残っていたのは、これが理由である（決定ログ索引の側にはテストが11件ある）。

## 申し送り

- 会話記録の置き場は `~/.claude/projects/c--Users-kaiki-Workspace-03-Dev-pergram/` だが、
  **担当エージェントの記録は直下ではなく `<セッションID>/subagents/agent-*.jsonl` にある**（サブディレクトリ）
- 担当エージェントの記録 72本での実測:

  | | 素の合計 | requestId で束ねた後 | 比 |
  | --- | --- | --- | --- |
  | usage を持つ行 / 往復 | 6,091 | 3,128 | 1.95 |
  | `input` | 12,180 | 6,254 | 1.95 |
  | `output` | 3,344,810 | 3,308,564 | 1.01 |
  | `cache_read` | 826,024,908 | 445,396,143 | 1.85 |
  | `cache_creation` | 42,392,040 | 17,778,470 | 2.38 |
  | **合計** | **871,773,938** | **466,489,431** | **1.87** |

- 同じ requestId の行は、`input` / `cache_read` / `cache_creation` が**完全に同一**。
  `output` だけが伸び、**最後の行が完全な値**（例: 1 → 1 → 218）
- `cache_creation` の比が行数の比より大きいのは、束ねる前に大きな値が重複しやすい記録が
  混じるため。**食い違いではない**
- Python は `python`（`python3` は入っていない）。**日本語を出すときは `PYTHONIOENCODING=utf-8` を付ける。**
  付けないとコンソールが cp932 で落ちる

  **`git status` に常に差分が出る。** これは異常ではない
