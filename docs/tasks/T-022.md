## 目的

**T-011（待機リストフォームの2段階化）で、ステップ2の見た目が壊れた。**

ステップ2はステップ1の送信後に現れる**完了状態（`.waitlist__done`）の中**に置かれている。
その完了状態カードは、もともと「ご登録ありがとうございます」の短い文言だけを中央寄せで
出すために作られており、**中にフォームが入ることを想定していない。**

T-011 の実装担当が報告した事象は2つ。

1. **`.waitlist__done { text-align: center }` がステップ2のフォームにも効き、ラベルが中央寄せになる。**
   入力欄のラベルが中央に来ると、どの欄の説明なのかが読み取りにくくなる
2. **`.waitlist` の枠がそのまま入るため、完了状態カードの中にもう1枚カードが入った
   二重枠に見える**

**実用上は読める**（実装担当がスクリーンショットで確認済み）。**壊れて使えないわけではない。**
ただしステップ2は、この製品が**次に何を作るかを決めるためのアンケート**であり
（`docs/research/validation-plan.md` §5 の「見たい成分」の内訳が P1 の成分選定に直結する）、
**回答率がそのまま判断材料の量になる。** 見た目の粗さが回答をやめる理由になりうる面である。

T-011 の実装担当は **🔒 `src/styles/` が自分の変更範囲外だったため、正しく触らずに報告した**
（共通の停止条件 S-4）。本タスクはその回付先である。

## 完了条件

1. ステップ2のフォーム内のラベル・入力欄が**左寄せ**になっている（`text-align` が
   `.waitlist__done` から継承されていない）
2. 完了状態カードの中で、フォームが**二重枠に見えない**（枠線・背景・角丸・余白のいずれかで
   カードの入れ子が視覚的に解消されている）
3. 完了状態の**見出し文言（「ご登録ありがとうございます」相当）は中央寄せのまま**である
4. 上記1・3 が `tests/styles.test.js` の自動テストで判定できる
5. 375 / 768 / 1440px で横あふれが 0px

## テスト方法

**単体（スタイルの不変条件）はこのタスクの担当が書く。**
`tests/styles.test.js` の既存のやり方（`src/styles/*.css` を読んで宣言を検査する）に倣う。
**座標を測る必要はない** —— 「`.waitlist__done` の中のフォームに `text-align: left` 相当が
当たっているか」「見出し側の中央寄せが残っているか」は、CSS の宣言として検査できる。

**実環境での目視確認が要る**（二重枠が実際に解消して見えるか）。**実施者はテスト担当。**
375px で確認する際は、**`--window-size` では meta viewport が無視され誤った観測になる。**
Chrome を `--remote-debugging-port` で起動し、Node 22 標準の `WebSocket` から
DevTools Protocol の `Emulation.setDeviceMetricsOverride`
（`width:375, height:812, deviceScaleFactor:2, mobile:true`）を叩くこと。
