# 組織改善の台帳

**書けるのはオーケストレーターだけ。** 担当エージェントは自分のタスクファイルの
`## 組織への指摘` に1行書く。**それをここへ吸い上げて起票するのがオーケストレーターの仕事である。**

担当エージェントがここへ直接書きに来ないのは、全タスクが触るファイルになると
(a) 同時に走る他タスクの書き込みが消え、(b) 並列に走らせられるタスクが無くなるためである。

**直す場所は、それを表現できる最も低い段を選ぶ**（`.claude/rules/org-improvement-feedback.md`）。

```
1. そのタスクの指示文を直す        ← いちばん安い。1タスクで閉じる
2. タスク別ファイルの雛形を直す
3. 層2の規約を直す
4. スキル（手順書）を足す・直す
5. 担当エージェントの定義を直す
6. 役を増やす・統合する            ← 1〜5 で解けないと分かったときだけ
7. 配布物そのものを直す            ← 全導入先へ波及する。いちばん高い
```

---

## 組織点検の記録

**組織点検を1回行ったら、ここへ1行足す。** 書式は次のとおり。

```
- YYYY-MM-DD 完了 N件時点 / 起票 N件 / エスカレート N件
```

`完了 N件時点` は、**その点検を行った時点で状態が `完了` になっていたタスクの数**である
（`python3 .claude/scripts/org-check.py --summary` の先頭に出る）。

セッション開始時に走る検査がこの数を読み、**「前回の組織点検から N 件完了」の1行を出す。**
次の点検の時期が、誰も覚えていなくても目に入るようにするための仕掛けである（目安は5件）。

**書けるのはオーケストレーターだけである。**

- （まだ1回も行っていない）

## I-001 完了条件が二値で判定できない形で書かれる

### 観測された事実（3件、いずれも別のタスク）

| タスク | 何が起きたか |
|---|---|
| **T-015** | 完了条件が「既存テストを ja / en の両方へ広げる」と**手段で**書かれていた。**そのとおり実施すると空振りのテストになる**状態だった（対象の文言が描画されなくなっており、旧文言を戻しても落ちない）。T-020 のレビュー指摘を経て条件が差し替えられて救われた |
| **T-021（T-006 由来）** | 完了条件が**生成物（`dist/`）だけ**を見ており、**配信の実態を見る条件が無かった。** 5件すべて充足していたが、本番では目的が達成されていなかった（Cloudflare が robots.txt を前置してAIクローラを全面ブロック） |
| **T-017** | 完了条件に `npm test` が通ることを置いたため、**同じ作業ブランチで並行している別タスクの未完成分で常に落ち**、このタスクの合否を自力で二値判定できなかった |

- T-017 は**他人の状態に依存する指標**を書いた（`npm test` 全体）

T-015 の担当が的確に言語化している —— **「条件が二値の観測（旧文言を戻すと落ちる）で書かれていれば、差し替え自体が不要だった」。**

### 検討の材料

雛形（`.claude/templates/T-XXX.md`）の `## 完了条件` の案内文は現在こうなっている。

> 二値で判定できる形。コマンドと出力で確認できること。
> 「正しく動くこと」は完了条件ではない。テストへ変換できるかで判定する

**「二値で判定できる形」だけでは、上の3つの落とし方を防げていない。** 3件とも
「コマンドと出力で確認できる」形式は満たしていた。

**なお、このセッションでは T-015 / T-019 / T-022 の完了条件を
「着手時点の件数から減らさない」形へ改め、並行担当由来の失敗はファイル名を報告する
扱いへ変えた**（段1の対処）。**3回目なので段2以上が要ると見ている。**

### 4件目（同日、T-019）— 代理指標のもう一つの形

ヘッダが2行に折り返してヘッダ高が 72 → 116px に増える変化を検出できない**
（折り返しても横あふれは 0px のままであるため）。

T-019 の担当は**初案が実際にこの状態になり、実測で気づいた。**
条件どおりに判定していれば、**折り返したヘッダのまま合格していた。**

T-021 と同じ「代理指標」の型である —— **横あふれが 0 であること ≠ 崩れていないこと。**


### 対応（2026-09-06。組織の定義を持つリポジトリ側で直した）

**適用範囲は配布物。** すべての導入先に入る。**この雛形が効くのは、これから起票するタスクだけである**——既存のタスクファイルは書き換えていない。

**期待する効果:** `[規約]` 種別で「完了条件が二値で判定できない」という指摘が、次の組織点検で0件になる。

## I-002 上流タスクの完了で下流の指示欄が失効するが、伝える手段が起動メッセージしかない

- 起票: 2026-09-02
- 出所: T-017（実装担当）`[規約]` / T-019 `[規約]` / T-020 の事後レビュー R-020-3 / T-009 `[規約]`（変更範囲の表と停止条件が同じファイルについて食い違っていた）

### 観測された事実

T-020（ヒーローの CTA をβ版1本に絞る）がマージされた結果、**未着手だった3タスクの指示欄が
同時に陳腐化した。**

| タスク | 何が失効したか |
|---|---|
| **T-018** | 完了条件1「待機リストの主CTAの上端が y<812」→ **その要素が存在しなくなり、達成不能になった** |
| **T-019** | 完了条件6「291件が全て」→ 件数が変わった。完了条件5 は T-020 が既に充足（二重作業になるところだった） |
| **T-017** | 完了条件1b の対象（`btn--quiet`）がヒーローから消えた。禁止事項「CTA の主従を変えない」が**ヒーローについてのみ失効**した |

**これらは T-020 の事後レビューが見つけた。** レビューを飛ばしていれば、
**達成不能な完了条件を持ったタスクへ担当を割り当てていた。**

T-017 の実装担当の指摘: **正しい読み替えは起動メッセージでのみ渡された。**
台帳の規約は「タスク別ファイルがそのまま作業指示」としているため、
**ファイルだけを読むと失効した禁止事項に従うことになる。**

### 検討の材料

- 台帳には `## 申し送り`（登録後に埋まる唯一の指示欄）がある。**今回もそこへ書いた。**
  ただし**書いたのは完了条件と禁止事項の本文のほうで、申し送りは補足だった** ——
  つまり運用としては機能した。問題は**気づく手段がレビューしかなかった**ことである
- 「上書き対象」の仕組みは**決定ログにはある**（`- 上書き対象: T-003 2026-05-10`）が、
  **指示欄（完了条件・禁止事項）にはない**
- 検査スクリプト（`org-check.py`）は指示欄が**空**であることは検出するが、
  **失効していること**は検出できない

### 続報（同日、T-019 の担当から）— 直し方の副作用

**オーケストレーターが指示欄を直した方法そのものにも問題があった。**

> `[規約]` 指示欄が起票後に3回書き換えられ、「⚠️ 2026-09-02 追記」と元の記述が
> 同じ節に並存している。**追記を読まずに元の行だけを読むと逆の作業をする**

**そのとおりである。** 失効した記述を残したまま「⚠️ 追記」を足す形にしたのは、
規約が「決定ログは書き換えず、上書きする新項目を追記する」としているのに
引きずられた判断だが、**決定ログ（履歴）と指示欄（作業指示）では要件が逆である** ——
履歴は過去を残すことに意味があり、**指示は今やるべきことが一意であることに意味がある。**

**この観測は I-001 とも繋がる**: 指示欄を後から直さざるを得なくなる原因の一つが、
最初に「何を確かめるか」ではなく「何をするか」で書いていることである。


### 対応（2026-09-06。組織の定義を持つリポジトリ側で直した）

**段3（オーケストレーターの手順）で直した。** 3つ入れてある。

1. **完了報告を受けたときの手順へ、番号付きで「下流タスクの完了条件と禁止事項が失効していないか見る」を追加した**（これまでは説明の節に書いてあるだけで、手順の並びに入っていなかった）
2. **見直す相手は「次の1タスク」ではなく、その変更が効く全ての未着手タスク**であることを、この課題の実例（1つのマージで3タスクが同時に失効した）とともに書いた
3. **「⚠️ 追記」で新旧を並存させることを禁じ、書き換えさせる形にした。** 決定ログ（履歴。消さない）と指示欄（作業指示。残さない）で要件が逆であることを表にした。続報で出た「追記を読まずに元の行だけを読むと逆の作業をする」への対応である

**検出は機械に持たせていない。** 指示欄が空であることは検査が言えるが、**書いてあるのに失効していること**は言えない。ここは人の目に残す。

**期待する効果:** 達成不能な完了条件を持ったタスクへ担当が割り当てられる事象が起きない。
**悪化しうるもの:** 完了報告のたびに見る対象が1つ増える。

## I-003 ブラウザでの目視確認の手順が、毎回書き捨てられている

- 状態: **診断済み**
- 起票: 2026-09-02
- 出所: T-020 `[道具]` / T-011（テスト担当）`[道具]` / T-009 / T-010 / T-017 / T-053 / T-057 / T-061 `[道具]``[反復]` — **8タスク・3セッションにまたがる**
- 適用範囲: **このリポジトリのみ**
- 適用範囲の根拠: 目視の手順書そのものは Web の成果物にしか要らない
- 段の見立て: **4（スキルを足す）**
- ⚠️ **関連: I-007。** この記録は「**人が目視するときの手順**」を扱う。**自動で回すフロントエンドのテストそのもの**は I-007 が扱い、そちらは PO 判断で **配布物**である

### 観測された事実

**同じ罠に、複数のセッション・複数の担当が繰り返し落ちている。**

| 罠 | 何が起きるか |
|---|---|
| ヘッドレス Chrome の `--window-size=375,812` でモバイル幅を見る | **端末エミュレーションを有効にしないと meta viewport が無視される。** デスクトップ幅のレイアウトが375pxの窓に切れて写るだけで、**「375px で右端が切れている」という誤った観測を生む。** 前セッションで実装担当2体が続けてここで詰まり、どちらも「375px は未検証」のまま完了報告した |
| `dist/` を `file://` で開く | **CSS を `/assets/...` の絶対パスで読むため、スタイルが当たらない。** エラーにならないまま**レイアウトの観測が誤る**（実際に `display:grid` が `block` に見えた）。ローカル HTTP 配信が要るが、**手順がリポジトリに無い** |

正しい手順（Chrome を `--remote-debugging-port` で起動 → Node 22 標準の `WebSocket` から
DevTools Protocol の `Emulation.setDeviceMetricsOverride` を叩く）は、
**毎回オーケストレーターが起動メッセージへ書き写している。** 依存パッケージの追加は不要。

### 検討の材料

- **この2つは「知らないと誤った観測をする」類であり、失敗が沈黙する。** テストが緑でも、
  目視の結論だけが間違う
- 前セッションの記録にも同じ内容がある。**セッションをまたいで再発している**
- スキル（呼ばれたときだけ読み込まれる手順書）にすれば、起動メッセージが短くなり、
  かつ担当が自分で呼べる


### 診断（2026-09-06）

**段は4（スキルを足す）で見立てどおり。ただし、作るスキルの中身はこのリポジトリ固有である**（ブラウザでの目視確認は Web の成果物にしかない）。**配布物の側では作れない。**

**配布物の側で直したのは、気づく仕組みのほうである。** オーケストレーターの手順の「層2を保守する」に、保守の引き金として **「同じ手順を、2回以上その場で書き起こした」** を足した。起動メッセージへ毎回書き写しているものがあれば、それはスキルへ出す合図である、と明示してある。

**残っているのはこのリポジトリ側の作業である** — `.claude/skills/` へ、ブラウザでの目視確認の手順（モバイル幅のエミュレーション、ローカル配信、`hidden` な要素の出し方）をスキルとして1本作る。**依存パッケージの追加は要らない**ことが観測で分かっている。

## I-004 変更範囲外のテストを実装が「回避」すると、判定側に独立検証の費用が発生する

- 状態: **適用済み**
- 起票: 2026-09-02
- 出所: T-011（テスト担当）`[規約]`
- 適用範囲: **配布物**
- 適用範囲の根拠: 段3（レビューの規約）で直した。変更範囲とレビューを持つ運用なら、どの導入先でも起きる
- 段の見立て: **未定**

### 観測された事実

T-011 の実装担当は、`tests/render.test.js:696` の判定（支援ウィジェットが完了状態の中にあるかを
正規表現で切り出して見る）が、**連続した `</div>` を領域の終わりと誤読する**ため、
ステップ2を完了状態に置くと壊れる構造であることに気づいた。

`tests/render.test.js` は**変更範囲外**だったため、担当は**テストを触らず、製品側の
マークアップ**（成分チップの並べ枠クラスの置き場）**を変えて当たらないようにした。**
規約どおりの正しい振る舞いである。

**その結果、テスト担当が「その回避が妥当か」を独立に検証する費用が発生した** ——
正規表現に頼らず `div` の対応を数え、切り出し終端が真の構造上の終端と一致することを確かめた
（偶然通っているのではないことの確認）。

### 検討の材料

- **これは規約が正しく働いた結果であり、規約違反ではない。** 費用が発生したという事実だけが観測である
- 代替案はいずれも高い: (a) 実装に範囲外のテストを直させる → 変更範囲の意味が消える、
  (b) 検証を省く → 回避が不変条件を壊していても気づかない
- **脆いテスト（正規表現での切り出し、文言文字列への依存、クラス名の完全一致）そのものを
  減らすほうが根本に近い。** T-020 のレビューも同種の指摘を3件出している
  （R-020-5 / R-020-6 / 既存事象5）

---

### 対応（2026-09-06。組織の定義を持つリポジトリ側で直した）

**段3（レビューの規約）で直した。** レビュー担当の定義へ、**修正先が `## 変更範囲` の外にしか無い指摘には `[範囲外]` を付し、そのタスクの通過判定から外す**という節を足した。オーケストレーターが別タスクとして起票するまでは消えたことにならない、という条件も入れてある。

**これは、この課題の観測（回避の独立検証に費用が発生した）そのものへの対応ではない。** そちらは記録のとおり「規約が正しく働いた結果」であり、代替案はいずれも高い。**直したのは、同じ根から出ているもう一方の症状**——T-010 で観測された「範囲外にしか修正先が無い Major を挙げると、そのタスクの中では絶対に解消できないまま要修正判定になる」——である。

**残っているのは「脆いテストそのものを減らす」ほうである。** 正規表現での切り出し、文言の完全一致、クラス名の完全一致に依存した判定を減らす話で、**これはこのリポジトリのテストの書き方の問題**であり、次の組織点検で改善エージェントが診断する。

### I-001 との関係

I-001 の「範囲を限定する」は、**他人の未完成分で落ちないため**の指示である。
**ここで起きているのは、その限定が効きすぎている側の症状**である。同じ指示の裏表であり、
**片方だけを強めると、もう片方が悪化する。**
