## 1. プロダクト

**pergram（パーグラム）** — サプリメントを「有効成分1単位あたりの価格」で横並びに比較する日本市場向けサイト。

サプリは剤形・含有量・内容量・価格・塩形態がバラバラで、「同じ成分を同じ量だけ摂るのにいくらかかるか」を比べる手段が実質存在しない。日本には公的なサプリラベルのデータベースもない。pergram はラベル表示の含有量を換算したうえで、単価で並べる。

### 立ち位置 🔒

**効能を提案するツールではなく、事実を計算して並べるツール。**

- 症状や悩みから商品を推薦しない
- 独自の「総合スコア」「おすすめ度」を作らない
- 出すのは、含有量・価格・公的基準値・認証という**検証可能な数値と事実のみ**

これは法務戦略そのものなので崩せない。

### 今回作るもの

**検証用ランディングページ（1枚）。** 公開前にメール登録を集め、どの成分に需要があるかを測る。

本体サービス（成分ランキング・製品詳細）は後続。ただし**同じデザインシステムで作る**ため、LP の設計はそのまま本体に引き継げる形にしてほしい。

## 2. 対象ユーザー

**数値を見る習慣がある層。** 価格.com や PCPartPicker を使いこなす人。

- 筋トレ目的でプロテインを**継続購入**している（＝年間コストが効く）
- セール時にまとめ買いする。個人輸入・iHerb を使う層が中核
- 「おすすめ10選」記事を信用していない
- **自分で計算したいが、面倒でやっていない**

痛みは「わからない」ではなく「**面倒くさい**」。
だから LP の仕事は教育ではなく、**「その計算、全製品ぶん終わってます」と見せること**。

## 3. このページが達成すべきこと

優先順。①が達成できていれば②③が弱くても合格、逆はない。

| # | 目的 | 判定 |
|---|---|---|
| ① | **「自分がいくら払っているか」に驚かせる** | スクロールせずに驚きが起きるか |
| ② | この計算が**全製品ぶん・毎日・中立に**行われていると伝える | 3つが数字と文言で示されているか |
| ③ | メールアドレスと「見たい成分」を受け取る | フォームまで到達するか |

### 何が「凄さ」なのか 🔒

**「1gあたりで計算する」こと自体は凄くない。** 英語圏には同じことをするサービスが既に複数ある（CompareProteinPrices は700製品超、ProteinMath は毎日更新、SuppsRadar は30成分を g/mg/IU に正規化）。日本語圏にも同種の記事がある。

**凄いのは次の3点だけ。** デザインはこの3つを可視化することに奉仕してほしい。

| 軸 | 競合の欠陥 | 可視化の材料 |
|---|---|---|
| **網羅性** | 「おすすめ10選」形式で、全体の中の最安が分からない | 掲載件数の実数。分布の形 |
| **鮮度** | 執筆時点の価格が残り続ける。プロテインは頻繁にセールする | 更新日時。価格の変動 |
| **中立性** | 上位記事はすべてアフィリエイト記事 | 順位の決まり方の明示。報酬と無関係であること |

## 4. 画面に必ず載るもの

### 4.1 製品1件について

| 要素 | 必須 | 備考 |
|---|---|---|
| **製品パッケージ画像** | ◎ | **v0.4 まで欠けていた。比較サービスとして必須** |
| ブランド名・製品名 | ◎ | 実名を出す。伏せると信憑性が消える |
| **主指標（有効成分1単位あたりの価格）** | ◎ | 行内で最も強い要素にする |
| 副指標（含有率・1食あたり価格・内容量など） | ◎ | 主指標より弱く |
| 順位 | ◎ | 順位は意味を持つ |
| 価格の取得日 | ◎ | 鮮度の証拠 |
| 出典（商品ページへのリンク） | ◎ | |
| 販売元 | ○ | |
| データの確からしさ | ○ | 低信頼の行を明示する（§6） |

#### 製品画像の扱い 🔒

- **効能を連想させる画像は禁止だが、パッケージ写真は事実の提示なので可。** 価格.com と同じ扱い
- **画像が存在しない製品が必ずある。** 欠損時の代替表現を設計に含めること。ブランド名の頭文字や無地のプレースホルダなど、**欠損が「壊れている」ように見えない**こと
- 画像の縦横比・背景色・切り抜きの有無はメーカーごとにバラバラ。**揃わない前提**でレイアウトを組むこと
- 画像が主役になって数値が負けないこと。**主役は数値**
- 画像の利用条件は取得元（楽天等）の規約に従う。**要確認事項として残っている**

### 4.2 ページ全体について

| 要素 | 必須 | 目的 |
|---|---|---|
| ロゴ + タグライン | ◎ | §5 |
| 掲載件数の実数 | ◎ | 網羅性の証拠。「たくさん」ではなく「68製品」 |
| 全体の更新日 | ◎ | 鮮度の証拠 |
| **単価の差がどれくらい大きいかの表現** | ◎ | 驚きの源。年額換算など |
| 並べ替え・絞り込みができると分かる表現 | ◎ | ツールであることを示す |
| メール登録フォーム | ◎ | §4.3 |
| 「このサイトがやらないこと」の宣言 | ◎ | 中立性。競合が誰も書いていない差別化 |
| 免責文 | ◎ 🔒 | 常時表示。折りたたまない |
| 数値の出典 | ◎ 🔒 | ラベル表示値であることを明記 |
| OGP 画像 | ◎ | SNS でそのまま読める密度 |

### 4.3 要望の導線（旧「フォーム」）🔒

**2026-09-07（T-051）にメールアドレス先行フォームを段構造へ置き換えた。**
広告の着地点である LP がいきなりメールアドレスという重い対価を求めていたため、
登録が 0 件だった。意思表示を1クリックまで下げ、メールアドレスは後段（任意）に置く。

**段は 要望 → アンケート → メール → 支援。この順を並べ替えない。**
LP と製品一覧で**同じ描画（`src/templates/request.js`）と同じ操作（`src/assets/request.js`）**
を共用する。🔒 片方へ写して2つ持たない — 2つあったから表記が割れた。

| 段 | 目印 | 対価 | 内容 |
|---|---|---|---|
| ① 要望 | `data-request-cta` | 1クリック | 押した時点で意思表示は成立。以降はすべて任意 |
| ② アンケート | `data-request-step="survey"` | 選択 | 見たい成分 / 普段の購入先 / その他の要望（自由記述） |
| ③ メール | `data-request-step="email"` | メールアドレス | 掲載時の通知。ここを飛ばしても次へ進める |
| ④ 支援 | `data-request-step="support"` | 任意 | Codoc。`support` を持たない市場では段ごと出さない |

**②〜④に `required` を付けない。** 要望は①で受け取っている。

| 項目 | 形式 |
|---|---|
| メールアドレス | 任意（③の段） |
| 見たい成分 | 複数選択（プロテイン / クレアチン / EAA・BCAA / HMB / 鉄・亜鉛 / ビタミン / その他） |
| 普段の購入先 | 複数選択（楽天 / Amazon / Yahoo! / iHerb / マイプロテイン / 店舗 / その他） |

**①の押下は GA4（`request_click`）と D1 の両方に残す** 🔒 —
`POST /api/request-signal` が `request_signal` テーブルへ UUID と日時の2列だけを1行入れる。
GA4 が CSP で全滅した実績があり（T-047）、計測が自分の手の中に無いと 0 件の意味が読めない。
重複はブラウザごと（`localStorage` の `pergram.request_signal_id`）に1件へ抑える。
**この行に UUID と日時以外の列を足さない。** 押された場所の区別は GA4 の `location` が持つ。

- **年齢・性別・体調は取らない** 🔒 — 要配慮個人情報であり、取る必要もない
- 購入先は**複数選択**（2026-08-10 に単一選択から変更）。掛け持ちが普通で、
  1つに丸めると提携の優先順位を決めるという本来の目的に使えなくなる。
  保存はカンマ区切り1列のままで、DB の列は増やしていない
- 「その他」は成分チップの1つで、自由記述欄はその**横**に並べる。
  独立した欄にすると、チップ未選択で書かれた要望を成分の希望と判別できない
- 「見たい成分」は**要望ボタンの直後（②の段）**に置く。ここが検証の主目的。
  2026-09-06 まではメールアドレスの直下だったが、そのメールアドレスが後段へ移った
- 送信後は同一ページ内で完了状態に切り替える。別ページに飛ばさない
- 完了文言に感嘆符を使わない

## 5. ブランド 🔒

| 項目 | 規則 |
|---|---|
| 表記 | **`pergram`** — 全て小文字。`Pergram` `PerGram` は不可 |
| 読み | パーグラム |
| 由来 | per gram — 1gあたり、というこのプロダクトの唯一の指標 |
| タグライン | **1gあたり、いくら払ってる?**（EN: What are you paying per gram?） |
| 初回接触 | **ロゴとタグラインを必ずセットで出す** |

タグラインを必ず添えるのは、`-gram` が Instagram / Telegram の連想を呼び、単体だと SNS アプリに見えるため。

**ロゴは未確定。** 現行案は「Archivo 800 のワードマーク + ルーラーティック（長短交互の目盛り）」だが、**提案を歓迎する**。要件は次の2つだけ。

- 小文字で組む（単位表記 `mg` `g` `mcg` が小文字だから。名前を単位と同じ字面の世界に置く）
- 禁止ビジュアル（§7）を使わない

## 6. 状態の設計

比較サービスは**データが欠けている状態が常態**。ここを設計しないと本番で崩れる。

| 状態 | 要件 |
|---|---|
| 製品画像がない | 代替表現を出す。空白にしない |
| 絞り込み結果が0件 | 「1つ外すと N 件になります」と、ワンタップで外せる導線 |
| 価格の取得に失敗 | 前回価格と取得日を出す。**空欄にしない** |
| データの確からしさが低い | 数値は出すが、根拠が弱いことを明示する |
| 公的な基準値が存在しない成分 | 「定められていません」と明示する。**推定値で埋めない** 🔒 |

**エラー文は謝らない。** 何が起きて、どうすれば直るかだけを書く。

## 7. 絶対制約 🔒

薬機法・景表法に直結する。**機能要件より優先し、迷ったらより保守的な方を選ぶ。**

### 使ってはいけない語
```
効く / 効果 / 改善 / 高品質 / おすすめ / 人気No.1 / 安心 / 話題の / 選ばれる / 実感
```

### 使ってよい語
```
単価 / 1gあたり / 含有量 / 含有率 / 元素量 / ラベル表示 / 比較 / 一覧 / 出典 / 更新日 / 安い
```

### 禁止事項

| # | 禁止 | 理由 |
|---|---|---|
| 1 | 成分の働き・体への作用に言及する | 薬機法 |
| 2 | 独自の総合スコア・おすすめ度・加重平均ランキングを作る | 事実提示ではなく推薦になる |
| 3 | 「だからこちらを選ぶべき」と書く | 判断はユーザーに委ねる |
| 4 | 症状・悩みの入力を受け付ける | 「症状→成分→商品」は効能の暗示 |
| 5 | **筋肉・肌・体のシルエット・before/after・人物写真** | 効能訴求と解釈されうる |
| 6 | **葉・植物・カプセル・錠剤・ハート・チェックマーク** | 効能または推薦を連想させる |
| 7 | LP にアフィリエイトリンクを置く | 広告審査でアフィリエイトサイト判定を受ける |
| 8 | ヒーローにダミーデータを置く | ここで嘘をつくと全部が崩れる |

**⑤⑥は「製品パッケージ写真」を含まない。** パッケージは事実の提示なので使ってよい（§4.1）。

### 数値の書き方

- 単位と基準を必ず添える。「¥38」ではなく「**¥38 / タンパク質1g**」
- 前提を必ず併記する。「1年で¥100,740の差」なら「60g/日 × 365日で計算」
- 「実測」と書かない。**ラベル表示値**であることを明記する

## 8. 技術的な下限

| 項目 | 要件 |
|---|---|
| **数値の字形** 🔒 | 等幅数字（`tabular-nums`）。桁が揃わない比較表は比較表として機能しない |
| **モバイル主** | 想定流入の大半がスマートフォン。390×844 で成立すること |
| タップ領域 | 44px 以上 |
| 本文サイズ | 16px 未満にしない（iOS のズーム発動を防ぐ） |
| 書体のライセンス | 商用利用可・無料（OFL 等）。**self-host できること**。日本語と英数字の両方が必要 |
| 書体の重み | 読み込むウェイト数を絞る。日本語フォントは重い |
| 色に依存しない | 状態・方向・警告を**色だけで表さない**。記号やテキストを併記する |
| コントラスト | 4.5:1 以上 |
| 動きの抑制 | `prefers-reduced-motion: reduce` を尊重する |
| マークアップ | 順位付きリストは `<ol>`、成分表は `<table>`。`div` で組まない |
| LCP | 2.0 秒以内。広告費を払って流入させるため離脱が直接コストになる |
| JS | フレームワーク不要。静的 HTML + 最小限のスクリプト |

**書体について**: 現行の指定は Archivo / IBM Plex Sans JP / IBM Plex Mono だが、**self-host していないため実装ではシステムフォントにフォールバックしていた**。つまり現物の見た目は指定と無関係。**書体選定は Claude Design に委ねる。** 上記の要件（無料・日本語対応・等幅数字・self-host 可）を満たせば何でもよい。

## 9. 配色のたたき台

**変更可。** 要件は「色数を絞ること」と「色だけで意味を担わせないこと」だけ。

| 用途 | 現行値 | 意図 |
|---|---|---|
| 本文・罫線 | `#14161A` | 純黒にしないのはラベル印刷の質感 |
| 背景 | `#FBFAF7` | ラベル紙の白 |
| 補足・出典 | `#6B6F76` | |
| 細罫 | `#DCD9D2` | |
| **強調** | `#1B44C8` | **「今見ている指標」の意味でのみ使う** |
| 認証バッジ | `#1F6F4A` | |
| 警告 | `#B3261E` | 上限量の超過のみ |

**強調色を安売りしないこと。** 全製品の価格を強調色にすると、その色は何も意味しなくなる。色を増やしたくなったら情報設計が間違っている合図。

### 世界観のヒント（拘束しない）

材料は**成分表示パネル**（米国 Supplement Facts / 日本の栄養成分表示）。太罫と細罫で階層を作り、左に名前・右に数値を置く表組みの文法。

これは装飾ではなく立場の宣言で、**「ここはマーケティングの場ではなく、ラベルの数値を読む場だ」**と言っている。この意図が伝わるなら、別のアプローチでもよい。

## 10. 参考にした事例

| サービス | 学ぶ点 |
|---|---|
| **Wise**（送金手数料） | ヒーローに実額を直接置く。翻訳の要る文言がなく**計算が語る**。名指しの比較で価格不安をその場の操作に変える |
| **Google Flights**（価格グラフ） | 予測をせず、実在する価格を並べて**分布の形**を見せる。数日ずらすと大きく変わることが「発見」として起きる |
| **価格.com** | 日本ユーザーの期待値の基準。**製品画像 + 絞り込みファセット + 最安値の即時提示** |
| **PCPartPicker** | 単一目的（組む）に全 UI を従属させる |
| **Camelcamelcamel / Keepa** | 価格履歴と「今が買い時か」の即答 |
| **SupplementMath / SuppsRadar**（競合） | 「30回分 vs 2lb」の表記差を剥がす説明の明快さ |

### 採らないもの

- **並列比較マトリクスをデフォルトにしない。** 大規模ユーザビリティテストで、ユーザーは比較対象を選ぶ段階でもスペックを読む段階でも困難を抱えることが分かっている。デフォルトは**単一指標で並んだ1本のリスト**
- 明るい配色・イラスト・グラデーションは、ラベルの質感と衝突する

## 11. 使えるデータ

設計時に「この値は出せるか」を確認しなくて済むよう、**実際に存在するフィールド**を挙げる。

### 製品ごと
```
ブランド / 製品名 / 剤形 / フレーバー / 内容量 / 1食のグラム数 / 1容器あたりの回数
有効成分量（1食あたり・換算後） / 販売元 / 価格 / 在庫 / 商品URL / 取得日
製品画像URL（※取得は実装可能。ライセンス要確認）
データの確からしさ（high / medium / low）
```

### 導出できる値
```
有効成分1単位あたりの価格（主指標） / 1食あたり価格 / 目標摂取量あたりの日額
100gあたり含有量 / 含有率 / 内容量 / 全製品の単価分布 / 絞り込み前後の最安差
```

### まだ無い値
```
第三者認証・原産国・添加物などの品質情報（後続フェーズ）
公的な推奨量・上限量（一次資料からの転記が未了）
レビュー評価（取得は可能だが表示は未定）
```

**現時点で実データは未収集。** 掲載件数・金額はすべて仮値であり、デザイン確定後に差し替える。**リアルなダミーで組んでよいが、実装時は実データに置き換わる**前提で。

## 12. 計測（実装時の要件）

デザインに影響する範囲だけ。**触られたかどうかを測れる形にしてほしい。**

| 測りたいこと | なぜ |
|---|---|
| デモ的な要素に触れたか | 価値が伝わったかの中間指標 |
| フォームに触れたか / 送信したか | 主 KPI |
| どこまでスクロールしたか | 離脱位置 |

**個人識別情報を計測に送らない。メールアドレスをイベントに含めない。** 🔒

### アフィリエイト表示について 🔒

**2026-08-08 の時点では「使っていない」と判断して開示を3箇所とも外した。**

**参加店舗が1件でもある以上、開示は常時出す。**

## 面の体系と字送りの階層（2026-09-08 / T-053）🔒

**PO がプレビューを見て「デザインがバラバラだ」と指摘した。** 主観の問題ではない。
製品一覧の主カラムに縦に積まれる4つの箱が、**角丸3種・背景3種・枠線3種・余白3種**を
持っていた。同じ階層の情報が4通りの見た目を持つと、読み手は「これは別の種類の情報だ」と
誤って受け取る。

この節は**面（サーフェス）の役割を3つに固定し、値の出所を1組のトークンへ寄せる**。
以後、箱を1つ足すたびに角丸と余白を決め直す作業は発生しない。

### 対象範囲

**この節が支配するもの** — 製品一覧と LP の主カラムに積まれる箱
（`.explainer` / `.notice` / `.request-band__inner` / `.request-flow__step`）と、
その中の字送り、要望ボタンの配置、段の開閉で残る器、見出しのフォーカスリング。

**支配しないもの** — 製品カード `.p-item` の内部（列割り・価格の組版）、絞り込みサイドバー、
ヘッダ・フッタ、LP のヒーローと帯（`.waitlist-band`）そのもの。
これらは既存のままで、面の役割の定義だけを共有する。

### 前提・制約

- **`tokens.css` の既存トークンの値を変えない。** `--signal` / `--signal-hover` /
  `--line-control` は WCAG 2.2 AA のコントラスト比を根拠に固定されている
  （根拠は `src/styles/tokens.css` の 🔒 コメント）。この節の設計は**既存の値を1つも
  動かさずに成立する**。動かさないと成立しない案は最初から採っていない
- **新しい色・寸法の「値」を1つも増やしていない。** 増やしたのは**役割の名前**だけで、
  新トークンはすべて既存トークンの別名である
- `.request-*` は **LP と製品一覧で共用**する（`src/templates/request.js` /
  `src/assets/request.js`）。片方だけ良くなる指定を書かない。文脈の差
  （LP は 640px の中央カラム、製品一覧は 900px 以上の広い主カラム）は
  **画面幅と、そのページにしか読み込まれない CSS ファイル**で吸収する
  （`site.css` = 共通 / `lp.css` = LP のみ / `products.css` = 製品一覧のみ）
- ⚠️ **この文書の §9「配色のたたき台」の16進値は実装と食い違っている**（青と緑が書いてあるが
  実装は橙系）。**色の値の唯一の出所は `src/styles/tokens.css` である。**
  §9 を見て配色を決めないこと（T-053 で気付いたが、修正はこのタスクの範囲外）

### 1. 面の役割は3つ 🔒

**増やさない。** 4つ目が要ると思ったら、それは情報設計が間違っている合図である。

| 役割 | 名前 | 何を割り当てるか | 見た目 |
|---|---|---|---|
| **A** | **読む面（カード）** | `.explainer` / `.request-flow__step` / `.p-item` | 白い面・細い枠・カードの角丸 |
| **B** | **呼びかけの面（帯）** | `.request-band__inner` | **A と同じ形。色だけが違う**（橙の淡い面と橙の枠） |
| **C** | **注記（面を持たない）** | `.notice` / `.request-form__note` / `.notice__beta` | **箱にしない。** 紙地の上の文字だけ |

**この3つで何が起きるか。**

1. **A と B は形が同じで色だけが違う。** 階層を**幾何ではなく色**で作る。
   幾何（角丸・余白）で階層を作ると、種類が増えるたびに新しい値が必要になり、
   今回の食い違いはそうやって生まれた。色は2つしか無い（`--signal` 系と無彩色）ので、
   色で階層を作るかぎり面の種類は増えようがない
2. **C は箱ではない。** 縦に積まれる箱が4つから2つへ減る。
   広告表示（`.notice`）を灰色の箱から出すのは**弱めるためではない**
   — 箱に入った定型文は「読み飛ばしてよい欄」に見える。本文と同じ地の上に、
   本文と同じ強さ（`--muted-strong`）で置くほうが、常時表示の趣旨に合う。
   ⓘ アイコンと文言はそのまま残す

**面の中に面を入れない。** A の中に A や B を置かない（`.request-flow__step` の中に
カードを作らない）。入れ子の箱は、この規模の画面では必ず階層の誤読を生む。

### 2. 各役割の具体値

**値はすべて `tokens.css` の新しい別名トークンから引く。** コンポーネント側に
角丸・背景・枠線・余白を直書きしない。

#### 2.1 `src/styles/tokens.css` へ足すトークン（追加のみ・既存値は不変）

角丸のブロック（`--radius-pill` の行）の直後に、次のブロックを足す。

```css

     🔒 面の役割は3つ。A 読む面 / B 呼びかけの面 / C 注記（面を持たない）。
        増やさない。値はすべて上の既存トークンの別名で、新しい色も寸法も足していない。
        コンポーネント側に角丸・背景・枠線・余白を直書きしないこと。 */
  --panel-bg: var(--surface);
  --panel-border: 1px solid var(--line);
  --panel-radius: var(--radius);
  --panel-pad: var(--space-4);
  --panel-pad-lg: var(--space-6); /* 900px 以上 */

  --panel-call-bg: var(--signal-band);
  --panel-call-border: 1px solid var(--signal-edge);

  /* スティッキーヘッダの高さ。アンカー移動とフォーカス移動の逃げ幅に使う。
     ⚠️ 同じ数値が lp.css（76 / 88px）と products.css（88px）に直書きで
        残っている。移行は T-053 の範囲外 */
  --head-offset: 76px;
  --head-offset-lg: 88px; /* 900px 以上 */
```

#### 2.2 面の値（A / B）

| 項目 | A 読む面 | B 呼びかけの面 |
|---|---|---|
| 背景 | `var(--panel-bg)` | `var(--panel-call-bg)` |
| 枠線 | `var(--panel-border)` | `var(--panel-call-border)` |
| 角丸 | `var(--panel-radius)`（= `--radius` 14px） | **同じ** |
| 内側の余白 | `var(--panel-pad)` / 900px 以上 `var(--panel-pad-lg)` | **同じ** |
| 面と面のあいだ | `var(--space-6)` | **同じ** |

**角丸を 16px（`--radius-lg`）から 14px（`--radius`）へ揃える。**
このページで最も多く出る箱は製品カード `.p-item`（14px）で、`.explainer` も 14px である。
16px を使っていたのは要望の帯と段の2つだけだった。**多数派へ寄せる。**
`--radius-lg`（16px）が残るのは**大きな面の2箇所だけ**である —— モバイルの絞り込みシート
`.filters`（`products.css`）と、LP の「順位が入れ替わる図」`.flip` の 900px 以上
（`lp.css`。900px 未満は 14px）。**新しい箱には使わない。**

> ✅ `.claude/rules/pergram-ui-copy.md` と `src/styles/tokens.css` の角丸の記述は、
> 2026-09-08（T-053 / R-053-3 / R-053-4）に上の2箇所を名指しする形へ直してある。
> 「全画面シート」という書き方は `.flip` を含まないので使わない。

**`.p-item` だけは 900px 以上でも `--space-4` のまま**にする。3列グリッドに並ぶため
1枚あたりが狭く、24px にすると中身の桁組みが崩れる。**意図的な例外であり、
「揃っていない」ではない**（`.p-item` は T-053 の変更範囲外でもある）。

#### 2.3 注記の値（C）

```
背景: なし / 枠線: なし / 角丸: なし / パディング: 0
アイコンと本文の間隔: var(--space-2)
前後の間隔: var(--space-3)（直前の面と同じ話題のとき） / var(--space-6)（話題が変わるとき）
```

#### 2.4 CSS の置き場（実装への指示）

**1つの規則が4つの面の幾何を決める。** `src/styles/site.css` の
「要望の導線と段階」ブロックの先頭に置く。

```css

**🔒 T-061 の追加 —— 帯の主文は T1、ボタンを挟む2つの条件は T4 で揃える。**
要望の帯（`.request-band`）だけは、**面の中に「その面の頭」が要る**。

字送りで宣言する。**新しい段（T0 など）は作らない** —— 「面の頭」という役割は

### 4. 要望の帯の組版（2026-09-08 / T-061 で全面改訂・2列）🔒

**この節は T-057 が書いた同じ番号の節を置き換える。** 差し戻しは3回目である（T-053 → T-057 → T-061）。

#### 対象範囲

**間違っていたのは「2列であること」ではない。** 間違っていたのは
**(a) 縦の揃え方、(b) 右列の中身の扱い、(c) ページごとに規則が割れていたこと**である。

#### 4.1 構図 — 左にテキスト、右に行動のブロック 🔒

```
┌─ .request-band__inner（面。全幅。§1 の役割 B） ────────────────┐

**列を2つの「箱」にする。** 左は `.request-band__text`、右は `.request-band__action`。
6要素をグリッドへ直接置かず、**列そのものを要素にする**。理由は2つ。

1. **列の中の軸が箱の幅で決まる。** 各列の中で全要素を `width: 100%` の block にすれば、
   左端は自動的に一致する（完了条件 B-1a）。要素ごとに `grid-column` / `grid-row` を配ると、
   1つ書き忘れた要素だけが別の場所へ落ちる（T-057 の指定が実際にそうなっていた）
2. **1列へ落ちるときに、箱ごと縦積みになるだけで済む。** 列の切り替えが1行の宣言で表せる

**🔒 `order` と `*-reverse` を使わない。** CSS Flexible Box Layout Level 1 §5.4 の規範文
（"Authors **must not** use `order` or the `*-reverse` values ... as a substitute for correct source ordering"）。
DOM 順で「ボタン → テキスト」と書いて見た目だけ入れ替えると、**Tab の移動順は DOM のまま残り**
WCAG 2.4.3 Focus Order（レベル A）に反する。
**DOM 順は 主文 → 副文 → マイクロコピー → 受領 → ボタン → 注記** で、視覚順と一致している（完了条件 B-4b）。
グリッドの明示配置（`grid-column`）は `order` ではないが、**本節では列の箱2つにしか使わない。**

#### 4.4 縦の揃え方 — 上そろえ 🔒

**`align-items: start`。垂直中央にしない。**

ベンチマークの実測11例では `align-items: center` が**7例で多数派**だが、
**分岐条件は左列の行数ではなく右列の中身**だった。

| 右列の中身 | 選ばれている揃え | 実例 |
|---|---|---|
| ボタン1個（またはボタンだけの行） | 垂直中央 | Primer / NICE / GOV.UK / Mailchimp / 楽天 / GitHub Copilot |
| **見出し・本文・ボタンの<ins>ブロック</ins>** | **`normal` / stretch（上そろえ）** | **GitLab（左右 583px / 50:50）/ DigitalOcean（左右 532px / gap 24px）** |

**pergram の右列はマイクロコピー + ボタン + 注記の3要素、すなわちブロックである。**
したがって**上そろえ**を採る。依る実例は **GitLab「Flex Commitment」と DigitalOcean のチュートリアル下部 CTA** の2例。

**⚠️ ベンチマーク本文の「含意 1」は「pergram も垂直中央で組むのが妥当」と書いているが、
これは pergram の右列を「ボタン1個」と仮定して書かれている**（同文書「問い1」の結論も同じ仮定に立つ）。
**仮定が事実と違うので、そちらは採らない。** 分岐条件そのもの（右列の中身で決める）は採る。

実測で**左列の中身の上端と右列の中身の上端の差は 0px**（完了条件 B-1b の 4px 以内）。

#### 4.5 列の幅と間隔 — 死んだ空白を構造で消す 🔒

```
grid-template-columns: minmax(0, max-content) minmax(20rem, var(--band-cta-max));
column-gap: var(--space-12);   /* 48px */
justify-content: start;
align-items: start;
```

**左列を `max-content` にすることが、死んだ空白を消す仕掛けである**（T-057 §4.5 から継承）。
列が左列の中身にぴったり吸い付くので、**左列の右端と右列の左端の距離は常に `column-gap`、つまり 48px になる。**
幅によって変わらない。完了条件 B-1c は測って満たすのではなく、**構造として満たされる。**

**🔒 左列を `1fr` へ戻さない。** 戻すと左列が余りを取り続け、1440px で 360px の穴が開く（T-057 が直した壊れ方そのもの）。
**🔒 `justify-content: space-between` にしない。** 右列が版面の右端へ飛び、B-1c が壊れる。
GOV.UK / NICE が `space-between` を採れているのは**右列がボタン1個で、帯が 795〜960px に収まっている**からである（§4.6）。

**右列の下限 20rem（320px）はボタンが要る幅から、上限 `--band-cta-max`（26rem = 416px）は
マイクロコピー（375px）と注記（337.5px）が1行に収まる幅から来ている。**

**🔒 右列のボタンは文字幅（`width: max-content`）。列いっぱいに伸ばさない。**
ベンチマークの含意 2 —— 実測11例中、右列のボタンを文字幅にしていたのが 9例、
列いっぱいに伸ばしていたのは Mailchimp と Zapier の2例だけ。ブロック型の2例も文字幅
（GitLab 196px / DigitalOcean 106px）。実測で pergram のボタンは **195.88px**（押下後 159px）。
**1列のときは全幅**（`width: 100%` / 上限 26rem）—— 親指で押す幅では全幅が正しく、
ベンチマークの縦積み時の姿とも一致する。

**縦の間隔（両方の列の中）**

```
主文 →（8px）→ 副文        ／  マイクロコピー →（8px）→ ボタン →（8px）→ 注記
```

**1列のときだけ、左の箱と右の箱の間に 24px を置く**（`.request-band__layout` の `row-gap`）。
**帯の中で広い間隔はここ1箇所だけ**で、上が「なぜ」、下が「いま押すもの」を分ける。
**差が意味を作る。** 等間隔にすると6つの独立した行になる。

マイクロコピーとボタンの間隔（8px）は注記とボタンの間隔（8px）と**同じ**（完了条件 B-5 は「同じか小さい」）。
**上下の条件が対称に挟む**という §4.2 の関係を、間隔でも表す。

#### 4.6 帯の版面 — 最大幅を置いて中央へ寄せる 🔒

```
.request-band__layout { width: 100%; max-width: var(--band-max); margin-inline: auto; }
--band-max: 54rem;   /* 864px */
```

**面（`.request-band__inner`）は全幅のまま、その中の版面だけを 864px で止めて中央へ寄せる。**
面を狭めない理由は §1 の「A と B は形が同じで色だけが違う」を守るためで、
`.explainer` と帯の面の外形はこれまでどおり一致する。

**なぜ最大幅が要るのか。** ベンチマークで**右端寄せのボタンを採っている実例は、いずれも帯が
795〜960px 程度に収まっていた**（NICE 795px / GOV.UK 960px / Primer は内側グリッド 1280px）。
**帯を無制限に広げるとその前提が崩れ、1440px で右列が孤立する**（完了条件 B-1d）。
ベンチマークの「(c) 主ボタンを右端へ飛ばすことは GOV.UK の指針とは逆向き」も同じことを言っている ——
右端寄せが成立するのは**左列の見出しから視線が横に流れれば届く距離**に収まっているときだけである。

**864px の出どころ。**

```
376.2（左列 = 主文の max-content）+ 48（列の間）+ 416（右列の上限） = 840.2px
→ 余裕を見て 54rem = 864px
```

**GOV.UK の 960px より狭く、NICE の 795px より広い。** 実測した右端寄せ実例の範囲に収まる。
**2列になる全ての幅で最大幅が効く**（1280px の版面 886px → 864px、1440px の 1006px → 864px）ので、
**版面の寸法は 2列である限り常に 864px で一定**である。1列では効かない（最も広い 768px でも 702px）ので、
**1列のときは帯の中身がページの軸（`.explainer` / 一覧と同じ左端）に乗る。**

⚠️ **中央へ寄せた結果、2列のときだけ帯の中身がページの軸から内側へ入る**
（1280px で 36px、1440px で 96px）。これは完了条件 B-1d が求めた挙動であって、ずれではない。
**「軸がずれている」と読んで `margin-inline: 0` に直さないこと。**

#### 4.7 1列へ落ちる幅 🔒

**帯そのものの幅が 50rem（800px）未満のとき1列にする。**
画面幅（`@media`）ではなく帯の幅（`@container`）で判定する（T-057 §4.4 から継承。理由は3つ）。

1. **画面幅と帯の幅が対応しない**（前提の表の非単調性）
2. **LP と製品一覧で分岐を書き分けなくてよい。** LP の帯は常に 640px なので、同じ1つの規則で自動的に1列になる
   —— これが完了条件 B-2（両ページで構図の作り方を割らない）を**構造として**満たす
3. **`@container` が効かない環境では1列のまま**になる。1列は B 群を単独で満たすので、
   **進歩的強化であって壊れ方を持たない。@media の代替を足さない**

**800px の出どころ。** 2列が成立するのは、**左列が主文の実寸 376.2px を丸ごと取れて、
なお右列が下限 320px を取れるとき**である。

```
376.2 + 48（列の間）+ 320（右列の下限） = 744.2px … 中身が使える幅
744.2 + 48（左右 padding）+ 2（枠線）    = 794.2px … 帯の外形
→ 余裕を見て 50rem = 800px
```

**ベンチマークとの対応。** 実例の1列化の閾値は **600〜800px が最頻**だが、**それらは画面幅である。**
pergram の帯は全幅ではない（900px 以上では左に絞り込みサイドバーが入る）ので、
画面幅と帯の幅が 1:1 で対応しない。**帯の幅 800px は最頻域の上端そのもの**であり、
画面幅に換算すると製品一覧で約 **1144px**、最も近い実例は **Primer CTABanner の 1012px**（`63.24rem`）である。

| 画面幅 | 帯の幅（製品一覧） | 組み方 | LP |
|---|---|---|---|
| 1440 | 1056 | **2列** | 1列（帯 640） |
| 1280 | 936 | **2列** | 1列 |
| 1024 | 680 | 1列 | 1列 |
| 900 | 556 | 1列 | 1列 |
| 768 | 736 | 1列 | 1列 |
| 390 / 320 | 358 / 288 | 1列 | 1列 |

**1列のときは、6要素すべてが `width: 100%` + `max-width: var(--band-cta-max)` の同じ箱になる。**
左端も中央も自動的に一致する（完了条件 B-1a の1列の読み替え）。実測で
**`xSpread` / `cxSpread` ともに 0px**、製品一覧・LP の両方で。

#### 4.8 折り返しの制御と字数の上限 🔒

**句読点折り返し**（`word-break: keep-all` + `overflow-wrap: break-word`）を T-057 から引き継ぎ、
**適用先を副文・マイクロコピー・受領メッセージへ広げる**（帯の5つの文すべて）。**対で置く。片方だけにしない。**
`text-wrap: balance` / `pretty` は日本語では解決しない（T-057 で実測済み）。

**🔒 帯の本文の1区切り（句読点から句読点まで）は 17 文字以内。主文は 13 文字以内。**
最も狭い測定幅 320px で中身が使える幅は **254px**。`--size-sm` は 12.5px なので 20 文字が限界、
17 文字（212.5px）なら 41px の余裕が残る。主文は 18px なので 254 / 18 = 14.1 → 13 文字。

| 文言 | 区切りごとの文字数 | 判定 |
|---|---|---|
| 主文 `request.lede` | 12 / 9 | ≤13 ✓ |
| 副文 `request.sub` | 12 / 15 | ≤17 ✓ |
| マイクロコピー `request.micro` | 13 / 17 | ≤17 ✓（**2026-09-08 / T-061 実装で字句を変えた。**下の §4.12 の ⚠️）|
| 注記 `request.note` | 16 / 11 | ≤17 ✓ |
| 受領 `request.receivedMessage` | 11 / 16 | ≤17 ✓ |

**文言を書き換えたら、この表を引き直す。** 18 文字を超える区切りを書くと、320px で語中折りが起き、
孤立行（完了条件 B-4）が生まれうる。

#### 4.9 状態 — 未押下 / 受領 / 押し直し 🔒

| 状態 | 見た目 |
|---|---|
| **未押下** | 左＝主文 + 副文。右＝マイクロコピー / 橙の面のボタン / 注記。受領メッセージは `hidden` |
| **押下直後** | **マイクロコピーが `hidden` になり、同じ枠に受領メッセージが出る**（T2 / 橙 / 700）。ボタンは `.is-received`（白地・橙の文字・橙の枠）へ退き、ラベルが受領の語に変わる |
| **押し直し** | **何も起きない。** 受領メッセージが既に出ていれば書き換えない |

**🔒 受領メッセージは「マイクロコピーと入れ替える」。別の場所へ足さない。** 理由は2つ。

1. **押した瞬間に帯の高さが変わらない。** 実測で 7幅・両ページとも未押下と受領の帯の高さが**完全に一致**する。
   注記の下へ足すと 22.5px 伸び、**押した直後にボタンが動く**
2. **視線がすでにその行にある。** マイクロコピーはボタンを押す直前に読まれた行である

**🔒 押し直しで受領メッセージを書き直さない。** `role="status"` は**中身が変化したときに読み上げられる**ので、
同じ文を書き直すと支援技術が2度読む。実装は「既に見えていれば何もしない」で守る。
**あわせて既存の 🔒 と対である** —— 決着の付いた段は開き直さない（`stepState` が `settled`）ので、
**空の器も復活せず `request_survey_view` も二重に飛ばない**（完了条件 C-3 / T-053 B-5b の回帰）。
**T-061 でそこへ手を入れる必要はない。**

**🔒 受領メッセージの文言は HTML に埋めず、押されたときに JS が書き込む。**
最初から入れて `hidden` を外すだけにすると `role="status"` の読み上げが飛ぶ
（`src/assets/request.js` の `finishStep` にある ⚠️ と同じ理由）。
**器そのものは初期状態で `hidden`** なので、JS が動かない環境でも帯は壊れない（完了条件 C-5）。

**動きは不透明度だけ、160ms。** 位置を動かすと上下の要素が押されて §4.5 の間隔が一瞬崩れて見える。
**`prefers-reduced-motion: reduce` の対応を新しく書かない** —— `site.css` の末尾に全称セレクタの
打ち消し（`animation-duration: 0.001ms !important`）が既にあり、これが効く（完了条件 C-4）。

**2列（製品一覧 1280 / 1440）**

| 測った量 | 完了条件 | 1280px | 1440px |

function markReceived(button) {

### 5. 空の器を消す（完了条件 B-5）

**現象**: アンケートを「回答せずに進む」で飛ばすと、`collapseStep()` が中のフォームを
`hidden` にするだけなので、**枠と余白だけの白いカードが画面に残る**
（1280px の実画面で確認済み）。

**推奨案 — 段そのものを畳む（`src/assets/request.js`、2行）**

```
collapseStep(kind): form.hidden = true;  step.hidden = true;   // 器ごと畳む
finishStep(kind):   collapseStep(kind);  step.hidden = false;  // 完了文言を出すので器は残す
```

- `.request-flow` は `display: grid; gap` なので、`hidden`（= `display: none`）にすれば
  **段の間隔ごと消える**。CSS 側の追加は不要
- 既存テスト「飛ばした段でもフォームは畳まれ、次の段が開く」は
  `[data-request-survey]` の `hidden` と**次の段**の `hidden` を見ており、
  **飛ばした段そのものは見ていない**。テストを書き換えずに通る
- ⚠️ **`openStep()` が無条件に `step.hidden = false` を行うと、畳んだ器が空箱のまま
  開き直す**（要望ボタンを押し直したとき）。設計時は「壊れない」と書いていたが、
  実装後のレビューで**フォームも完了文言も隠れたままの高さ 50px の空箱**が
  復活することが実ブラウザで確認された（T-053 / R-053-1）。段は
  `idle` → `open` → `settled` の状態を持ち、**`settled` からは開き直さない**。
  閲覧イベント（`request_survey_view`）も `idle` から出るときだけ送る

**併せて必要な変更 — 先頭の段の上の余白**

現状 `.request-flow__step:first-child { margin-top: var(--space-8) }` が
「リストと段のあいだ」を作っている。**先頭の段（アンケート）を畳むと、
2番目の段（メール）はこの余白を持たない**（`:first-child` は構造上の指定で、
`display: none` を無視するため）。器の側へ移す。

```css
/* 🔒 器そのものに余白を持たせるのは、見えている段が1つ以上あるときだけ。
      全部閉じている初期状態で空白だけが残るのを避ける（T-050 の 🔒 の言い換え）。 */
.request-flow:has(> .request-flow__step:not([hidden])) {
  margin-top: var(--space-6);
}
.request-flow__step:first-child { margin-top: 0; } /* 旧指定は消す */
```

LP 側（`lp.css`）の `.waitlist-band .request-flow__step:first-child { margin-top: var(--space-6) }`
は、**移さずに削除した**（2026-09-08 / 実装時の判断。T-053 決定ログ
「LP の先頭の段の余白は `:has()` へ移さず、規則ごと削除する」）。移した後の値は
上の `.request-flow:has(...)`（`--space-6`）と**同値**であり、lp.css へ写すと
同じ値の出所が2つになる。lp.css 冒頭の 🔒 が「段そのものは site.css が唯一の出所。
ここへ写して上書きしない」と明記しており、**今回直している「出所が2つある」問題を
直した直後に作ることになる**。LP の実画面（1280px / 390px）で段の上の余白が
従来どおり出ることは確認済み。`:has()` が無い環境では余白が付かないだけで、崩れはしない。

**採らなかった案**

- **CSS だけで消す**（`.request-flow__step:has(> .request-form[hidden]):not(:has(...))`）
  → 二重否定の `:has()` は読めない。次に触る担当が意味を復元できない
- **飛ばしたときにフォームを元へ戻し、段を初期状態へ返す** → 一見きれいだが、
  既存テストが「飛ばしたらフォームは畳まれている」を検査している。
  仕様変更としてテストの書き換えが要り、視覚の修正に混ぜる変更ではない

**未解決（この設計では直さない）**: 段を畳んでも要望ボタンの `aria-expanded` は
`true` のままで、**開いていない領域を開いていると言っている**（WCAG 4.1.2）。
**状態機械の設計として別タスク（T-054）で扱う**。
なお「押し直すと空の段が開く」ほうは T-053 の実装で塞いだ（上の ⚠️）ので、
T-054 が扱うのは `aria-expanded` の値そのものだけである。

### 6. フォーカスリングの見せ方（完了条件 B-6）

**現象**: `.request-flow__heading` は `tabindex="-1"` で、段が開いたとき
`src/assets/request.js` がプログラム的にフォーカスを移す。見出しはブロック要素なので、
`:focus-visible` の輪郭が**段の全幅**に出て「壊れた要素」に見える。

**決定 — 可視性は落とさず、輪郭を文字に沿わせる**

```css
/* 🔒 段が開くとここへフォーカスが移る（src/assets/request.js）。
      ブロック要素のままだと段の全幅に枠が出て壊れて見える。
      **輪郭を消さない**（WCAG 2.4.7 / 2.4.11）。文字に沿わせるだけである。 */
.request-flow__heading {
  width: fit-content;
  max-width: 100%;
  scroll-margin-top: var(--head-offset);
}
.request-flow__heading:focus-visible {
  outline: 2px solid var(--signal);
  outline-offset: 4px;
  border-radius: var(--radius-interactive);
}

@media (min-width: 900px) {
  .request-flow__heading { scroll-margin-top: var(--head-offset-lg); }
}
```

- **太さ 2px を維持する。** 色は `--signal`。白い面（`--surface`）に対して 5.18:1 で、
  非テキストコントラストの下限 3:1 を満たす（根拠は `tokens.css` の 🔒 コメント）
- `outline-offset` を 2px から **4px** へ広げる。文字に沿った小さな枠になるので、
  近すぎると字に食い込む
- `border-radius` を付けて、輪郭を他の操作（ボタン・入力欄）と同じ丸みにする
- **`scroll-margin-top` を足す理由**: フォーカス移動と同時に
  `scrollIntoView({ block: 'start' })` が走るため、現状は**見出しがスティッキーヘッダの下に
  潜る**（WCAG 2.4.11 Focus Not Obscured）。B-6 の文言には無いが、同じ操作で起きる
  同じ壊れ方なので併せて直す

**採らなかった案**

- **フォーカスの対象を段の器（`.request-flow__step`）へ移す** → 枠がさらに大きくなる。逆効果
- **輪郭をやめて背景の色替えにする** → 装飾に見えるうえ、面の色を増やすことになる（役割は3つ）

### 7. 文言 — 礼を先に置く

**現状**: 要望ボタンを押した直後に出る最初の文が
「回答は任意です。リクエストはすでに受け取りました。」で、**礼を言う前に免責から入っている。**
押した人の行動を否定する語順になっている。

**決定**

| 操作 | キー | 値 |
|---|---|---|
| **追加** | `request.surveyThanks` (ja) | `リクエストありがとうございます。もしよければ任意で詳しくご要望をお聞かせください。` |
| **追加** | `request.surveyThanks` (en) | `Thanks for your request. Tell us more if you like — it is all optional.` |
| **削除** | `request.surveyLede` | ja / en とも**キーごと消す**（描画箇所も消す） |

- 「任意です」は**礼と依頼の中に溶かす**（「もしよければ任意で」）。
  独立した免責の一文として先頭に置かない
- 禁止語（効く / 効果 / 改善 / 高品質 / おすすめ / 人気No.1 / 安心 / 話題の / 選ばれる / 実感）
  を含まない。感嘆符を使わない
- `request.surveyLede` を消しても、アンケートが任意であることは
  「回答せずに進む」ボタンと `request.surveyThanks` の「任意で」が担う

**差し込む位置** — `src/templates/request.js` の `surveyStep()`。
**`<form>` を開いた直後、見出しより前**に置く。

```
<form class="request-form" data-request-survey novalidate>
  <p class="request-flow__thanks">…request.surveyThanks…</p>   ← 追加
  <h2 class="request-flow__heading" tabindex="-1">…request.surveyHeading…</h2>
  <p class="request-flow__lede">…request.surveyLede…</p>        ← この行ごと削除
  <fieldset …>
```

- フォームの中に置くので、送信・スキップでフォームが畳まれると礼の文も一緒に消える。
  **完了状態に礼の文が残らない**
- `.request-flow__thanks` の字送りは **T3**（本文・リード）。
  **新しい字送りの役割を作らない** — 受け取ったことは要望ボタンが
  「リクエストを受け取りました」へ変わることで既に示されており、二重に強調しない

**⚠️ 併せて必要な `src/assets/request.js` の変更（変更範囲の但し書きの拡張が要る）**

段を開くとき、現在は**見出しを画面上端へスクロールさせている**
（`bringIntoView(heading)`）。このままだと、**見出しより前に置いた礼の文が画面の外へ出る。**
完了条件 A-2 の文字列検査は通るが、**PO が求めた「礼を先に読ませる」は実現しない。**

```
heading.focus({ preventScroll: true });   // フォーカスは見出しへ（読み上げの起点は変えない）
bringIntoView(step);                      // 画面へ出すのは段の器（礼の文を含む）
```

`preventScroll` に対応しない環境では無視されて現状の挙動に戻るだけで、壊れない。
`.request-flow__step` にも `scroll-margin-top: var(--head-offset)` を付ける。

**T-053 の変更範囲は `src/assets/request.js` を「空の器が残らないようにする場合のみ」と
書いているため、この1点はオーケストレーターの承認が要る。**

### 10. この設計で名前を付けたもの

| 語 | 意味 |
|---|---|
| **面の役割（A / B / C）** | 縦に積まれる箱の種類。A = 読む面（カード）、B = 呼びかけの面（帯）、C = 注記（面を持たない）。**3つで固定** |
| **パネルトークン**（`--panel-*`） | 面の見た目の唯一の出所。既存トークンの別名であり、新しい値ではない |
| **字送りの階層 T1–T6** | 面の中の文字の役割。見出し / ラベル・受領 / 本文・リード / 条件の注記 / 微注記 / 入力のラベル |
| **`--head-offset`** | スティッキーヘッダの高さ。アンカー移動とフォーカス移動の逃げ幅 |
| **`.request-flow__thanks`** | アンケートの段の冒頭、見出しより前に置く礼と依頼の1段落 |
| **`request.surveyThanks`** | 上の文言のキー |
