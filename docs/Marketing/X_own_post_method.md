## 0. この文書の位置づけ

**単体で読んで、明日から何を投稿すればいいかが分かることを目的にしている。**
`X_growth_design.md` を読まなくても実行できる。

**この文書が置き換えるもの**: `X_growth_design.md` §3.2〜§3.3 のうち、**リプライに関する手順
（意図層リプ・露出層リプ・watchlist の運用）**。これらは今後 **PO が個人の判断で行う、
機構の管理外の補助経路**になった。機構（`.media-agent/`）が生成・検査・登録・集計するのは
**自前ポストだけ**であり、本文書はその方法を定める。

**この文書が置き換えないもの**: `X_growth_design.md` の一次情報の解説（§1・§2.6・§2.7 など）、
禁止語・ブランド表記（`rules.md` / `pergram-ui-copy.md`）、既存の投稿の型の定義そのもの
（ranking-doubt / whats-inside / not-comparable / build-in-public / price-on-request）。
**型は引き継ぐ。型の選び方と時間配分を変える。**

**リプライについての注記**: PO が手動で行うリプライ（他人のスレッドへの意図層・露出層リプ）は、
本文書が定義する自前ポストの時間予算・KGI 貢献の計算に**含まない**。PO がどれだけ行うかは
PO 自身の裁量であり、機構はそれを前提にした設計をしない（前提にすると、PO が行わなかった場合に
設計全体が空振りする。今回の起票理由そのものである）。

## 1. 何を最大化するか

出典: [X_algorithm_findings.md](X_algorithm_findings.md) §1.2（一次情報・本番既定値）。

| 行動 | 重み | いいね比 | この設計での扱い |
|---|---|---|---|
| **リンクをコピーして共有** | `share_via_copy_link` **20.0** | **40倍。全行動中で最大** | **最優先で狙う** |
| リプライ（自分の投稿が受け取る） | `reply` 5.0 | 10倍 | **二番目に狙う**（price-on-request） |
| 引用リポスト | `quote` 5.0 | 10倍 | 狙って作るが主軸にはしない（3節） |
| 著者をフォロー | `follow_author` 4.0 | 8倍 | 会話の結果として起きるものを受け止める。狙って集めない（§2.7、一括フォローは規約違反の挙動として検出対象） |
| 共有（メニュー） | `share` 2.0 | 4倍 | コピー共有と同じ作り方で自然に付いてくる |
| リポスト | `retweet` 1.0 | **2倍** | **狙わない。** 二次情報の「20倍」は 2023年当時の推計で、一次情報の10分の1しかない |
| いいね | `favorite` 0.5 | 基準 | 基準値。狙う対象にしない |
| **プロフィールをクリック** | `profile_click` **0.0** | **0倍** | **ランキングには効かない。事業上の変換指標としてのみ使う（下記）** |
| 通報 | `report` **-234.0** | 一撃で沈む | 出典・取得日を必ず添え、誤った数字を出さないことで避ける（§1.6a 相当の慎重さを常に保つ） |

### 何を最大化しないか、が重要である

**プロフィールクリックは、増えても次の露出が増えるわけではない。**
`profile_click` の重みは 0.0 であり、押されても順位計算に一切乗らない
（findings §1.3 W-2 / `X_growth_design.md` §2.2b）。

これは「プロフィールクリックを見るのをやめる」という意味ではない。**流入の変換（プロフィール →
固定ポスト → LP）は依然としてここで起きる。無効なのは「プロフィールクリック率が上がれば、
X 側の配信量そのものが増える」という因果である。** この2つを混同すると、
「クリック率の高い型を伸ばせば imp も伸びる」という誤った打ち手を取ってしまう。

**imp（配信量）を伸ばす変数は `share_via_copy_link` と `reply` であり、プロフィールクリック率ではない。**
Day7 のゲート（`X_growth_design.md` §7.2）でこの2つを混同しないこと（§6 に詳述）。

**リポストとブックマークも狙わない。** リポストは重みが低く（2倍）狙う労力に見合わない。
ブックマークはランキングに使われる行動の一覧に存在せず、寄与はゼロである（findings §6.1）。

## 2. 自前ポストの2つの型 — 実際に作れる形

**狙う行動ごとに、作り方が違う。** どちらも既存の型（`X_growth_design.md` §6）の中にある。
新しい型を作る必要はない。**選び方と力の入れどころを変える。**

### 2.1 送りたくなる投稿（`share_via_copy_link` を狙う）

**当てはまる型**: whats-inside / not-comparable / ranking-doubt

**作り方の規則**（`X_growth_design.md` §5.4 を引き継ぐ）:

1. **リンクだけを渡されても意味が通ること。** 送られた先の人は元の会話の文脈を持っていない
2. 数え上げ・レンジ・単位の定義を**表の形か、それに準じた短い箇条書き**で置く
3. 数字は1投稿に2つまで（§5.2 N-1）。率ではなく重量で書く（N-2）。単位と基準を必ず添える（N-3）
4. 件数と取得元をセットにする。網羅を示す語（全メーカー・全比較）を使わない（C-3）
5. **引用されたい投稿ほど、自分の限界を先に書く。** 「46製品・楽天のみですが」を隠さない

**実例（2026-09-02 時点の実データ。投稿前に必ず再計算する）**:

```
[whats-inside]
同じ1kgのプロテインでも、中身のたんぱく質量は製品によって全然違います。

楽天で取れた46製品だと、1kgあたり330g〜936g(2.84倍)でした。
9/2までに取得。

pergram — 1gあたり、いくら払ってる?
```

```
[not-comparable]
「1食の量」ってメーカーによってバラバラで、比べようがないんですよね。

楽天で取れた46製品のうち、1食あたり表示は34製品(13g〜30gで11通り)。
残り12製品は「100gあたり」表示で、そもそも1食が決まっていません。

pergram — 1gあたり、いくら払ってる?
```

```
[ranking-doubt]
「おすすめ順」って、何を根拠に並んでいるんでしょうか。

pergramは、たんぱく質1gあたりの単価だけで並べています。
報酬額は下書きにも保存していないので、報酬の高い順を作れません。
46製品・楽天のみですが。
```

**画像を付けられる場合**（T-041 完了後）は `X_growth_design.md` §5.7 の「数字だけのカード」を
1枚目に添える。**画像が無くても本文だけで送れる形にしておく**（T-041 を待たない）。

### 2.2 返信を引き出す投稿（`reply` を狙う）

**当てはまる型**: price-on-request

**作り方の規則**（`X_growth_design.md` §2.3 / §6.5 を引き継ぐ）:

1. 「商品名を教えてもらえたら、たんぱく質1gあたりの単価を計算して返す」と申し出る
2. なぜ分かりにくいのかを1文（袋の値段と内容量からは出ないから）
3. 手元の数字を1つ置く
4. **返ってきた商品名には必ず全件返す。返せない量を集めない**（返信も `reply` として自分の投稿の
   スコアに乗るが、**返さないまま放置すると「宣伝して逃げた」と読まれ、`report` / `mute_author` の
   引き金になりうる**（findings §1.2 の負の重み一覧））

**実例**:

```
[price-on-request]
おはようございます☕ 今日も1gあたりの話をします。

飲んでいるプロテインの商品名を教えてもらえたら、
たんぱく質1gあたりの単価を計算して返します。

楽天で取れた46製品だと¥1.92〜¥34.55まで開きました(9/2までに取得)。
```

**やらないこと**（rules.md / N-01 / N-05 / N-03 と同じ）: 症状・目的・体調を聞かない。
「どれがいいか教えます」と書かない（推薦ではなく計算）。46製品に無い製品は出典と取得日を必ず書く。

### 2.3 狙わないが、結果として起きるものへの対応

**引用（`quote`）** はランキング狙いでは書かない。ranking-doubt の「反証可能な言い切り＋自分の限界」
という作り方（§5.4 に既述）が結果として引用を誘発する。**引用そのものを目的化した文面は作らない**
（反証可能な言い切りを乱発すると N-03・C-5 に近づく）。

**フォロー（`follow_author`）** は会話が成立した相手を**フォローし返す**（§2.7）。
一括フォロー・フォロー狙いの行動は取らない（`bdsm/` / `agatha` の検出対象になりうる）。

## 3. 新規著者ブースト（cold start）の使い方 — 前提を置かない

出典: [X_algorithm_findings.md](X_algorithm_findings.md) §3.1 / `X_growth_design.md` §2.6。

**使えるところだけ使う。適用されているかを前提にした計画は立てない。**

| 条件 | @pergram_jp の状態 | この設計での扱い |
|---|---|---|
| フォロワー1,000以下 | 満たす | **何もしなくてよい。**14日で1,000超に到達する見込みは無い |
| ホーム表示1,000未満 | 満たす（実測17imp） | **何もしなくてよい。**上限にはまだ遠い |
| リプライ・リポストではない | 自前ポストは満たす | **これが「リプライを主軸から外す」ことの直接の利点である。** リプライはこの優遇の対象外 |
| 投稿が24時間以内 | 常に満たせる（毎回新規投稿） | **「30分で数字が動かないと終わり」という通説は採らない**（一次情報に無い。findings §2.1）。**投稿後24時間はまだ終わっていないという前提で運用する**（削除や差し替えを焦らない） |
| **閲覧者の実験群と著者のバケットが噛み合っている** | **不明。観測できない** | **ここを前提にしない。** ブーストが効いていてもいなくても成立する設計にする（§1・§2 の型はブースト無しでも作れる内容である） |

**結論**: cold start boost は「効いていれば追い風」程度の扱いにとどめる。
**投稿本数や投稿時刻を、ブーストが効くことを前提に決めない。** 本数は §5 の時間予算から決める。

## 4. 可視性ラベル（U-3）の扱い

自前ポストが 17imp に留まっている原因の候補は3つ（`X_growth_design.md` §10 U-8）。

| # | 候補 | 観測できるか |
|---|---|---|
| ① | 可視性ラベルが付いている（`DO_NOT_AMPLIFY` / `SPAM_HIGH_RECALL` 等。findings §4.1） | **できる（下記の方法で）** |
| ② | 投稿の中身が弱い | 型を変えて比較すれば分かる |
| ③ | 新規著者ブーストがそもそも適用されていない（実験群の条件） | **できない** |

①が最も重い（ラベルが付いていれば、②③を直しても無意味）。**したがって①を先に確認する。**

**確認方法**（`X_growth_design.md` U-3 の解決策を踏襲）: ログアウト状態のブラウザで
`@pergram_jp` を検索し、自分の投稿が検索結果に出るかを見る。

**頻度**: 毎日は行わない（機構管理外の手作業の枠を圧迫するため）。

- **導入時に1回**（本メソッド適用開始日）
- その後は**3日に1回**
- **例外**: 2日連続で imp が明確に落ちた（それまでの中央値の半分未満）ときは、次の確認を待たずに即確認する

**確認できなかった場合の扱い**: ログアウト検索は間接的な代理指標であり、
「出ている＝ラベルが無い」の確認にはなるが、「出ない＝ラベルがある」を断定はできない
（検索インデックスの遅延等、別の理由でも起こりうる）。**断定できない場合は「ラベルは無い」と
仮定して§1・§2 の方法を続ける。** 仮定が誤っていた場合の検知は、Day7 相当のゲート
（`X_growth_design.md` §7.2 に準じる）で「share_via_copy_link 狙いの投稿を続けても imp の中央値が
上がらない」という結果から間接的に行う。**推測で「ラベルがある」と決めつけて運用を止めない**
（止める根拠にできるのは検索結果で確認できたときだけ）。

## 5. 1日の運用 — 機構が出す／人が決める／人が手で打つ

**リプライ（意図層・露出層）はこの表に含まれない。PO が別途、個人の判断で行う。**

### 機構が出す（既存の生成・検査の仕組みを使う。新規の機構変更は要求しない）

- その日の自前ポスト下書き（§2.1 / §2.2 の型からのローテーション。数字は `data/products.json` から
  その都度再計算）
- 禁止語・上限のチェック（PolicyEngine を通す。既存）
- 承認キューへの登録

### 人が決める（目安 5分/日）

- 承認キューの下書きを読み、必要なら文面を調整して承認する
- ニュース・セール等の「窓」（`X_growth_design.md` §2.4 相当）に当たったら、その日の型を
  差し替えるかどうかを判断する。**毎日探しに行く手順は置かない**（それは露出層リプの探索手順であり、
  本文書の対象外。自前ポストは能動的な窓探索が無くても §1・§2 だけで回る）

### 人が手で打つ（目安 15〜20分/日。3日に1回は+3分）

| 作業 | 分 | 理由 |
|---|---|---|
| ツリー2投稿目（リンク）を手でぶら下げる | 6（3分×2回） | Buffer がツリーに未対応のため（T-037 で解消見込み） |
| 自分の投稿に来た返信へ全件返す（price-on-request 含む） | 5〜10（反応量に応じる） | §2.2。返さないと負の重みの引き金になりうる |
| 日次記録1行（imp・返信数・共有数の分かる範囲で） | 3 | Day7 相当の判定に使う |
| 可視性ラベルの確認（§4） | 3（3日に1回） | — |

**合計: 約15〜20分/日。** 旧来の制約（`X_growth_design.md` 前提 A-1: 1日60〜90分、3分割）から
大幅に減っている。**理由は、意図層リプ7件・露出層リプ4件（合計51分。§3.2 の手2・6・9・10）が
PO の個人作業として本文書の予算の外へ出たため。**

浮いた時間の使い道は PO の裁量とするが、**この方法自体は追加投入を前提にしていない。**
§1・§2 の型は現状の生成・承認の仕組みで賄える範囲で設計してある。

## 8. 採用しなかった案と却下理由

| 案 | なぜ却下したか |
