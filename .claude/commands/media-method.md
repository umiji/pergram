# 投稿メソッドの構築

対象アカウント: `$ARGUMENTS`

**あなたのロールはアナリスト / マーケターである。** 投稿は書かない。
「いま何が、なぜ伸びているか」を突き止めて、書く人が使える設計図に落とすところまで。

**このコマンドは投稿を行わない。** 毎回回すものでもない — 週次〜月次、または伸びが
鈍ったときに回す。

## この作業は4段のうち①と②である

**型の抽出と、ペルソナへの当てはめは、別の段である。** ここを1つにすると、
「自分の題材に近い投稿」を探しに行って母集団を潰す（2026-09-08 に実際に起きた）。

| 段 | やること | 題材を見るか | 担当するコマンド |
| --- | --- | --- | --- |
| **①** | **いま何の型で伸びているかをリサーチする** | **見ない。題材は問わない** | **このコマンド** |
| **②** | **型ごとにスロットへ落とす（定型手順化）** | **見ない。中身は空のまま** | **このコマンド** → `structures/` |
| ③ | ペルソナ・サービスに合うテーマを選ぶ | **ここで初めて見る** | `/media-strategy`（扱うテーマ）と このコマンドの手順 0（読み手） |
| ④ | テーマを型へ流し込んで書く | 見る | `/media-draft` / `/media-content` |

**①②で「この投稿はうちの読み手に関係あるか」を判定してはならない。**
借りるのは骨組みであって題材ではない。関係の有無を見るのは③である。

## 先に読むもの

- `.media-agent/<アカウント>/strategy.md` — 扱うテーマと扱わないテーマ
- `.media-agent/<アカウント>/personas/` — 読み手
- `media-agent knowledge show x/discovery-distribution` — 何が加点・減点か（B 層）
- `media-agent knowledge show x/formats` — 形式と長さの上限（B 層）
- `media-agent knowledge show discipline/learning` — 観測から型を取る手順（A 層）
- `.media-agent/<アカウント>/structures/` — 前回までに作った骨格

## 手順

### 0. 読み手を確かめる（無ければ先に作る / あれば見直す）

`personas/` を見る。**1 件も無い、または雛形のまま（各項目が「（未記入）」）なら、
ここで先にペルソナを作る。** ペルソナが無いままクエリを設計すると、このプロジェクトと
関係のない一般ジャンルを調べに行き、取れた骨格も誰にも刺さらない。

1. `strategy.md` の「ターゲット」と「コンテンツ方針」を読む。**ここが未記入なら人に聞く。**
   推測で埋めない
2. プロジェクトの実体（README・製品・扱っているデータ）から、読み手が実際に困っている
   ことを拾う
3. **2〜4 人に分ける。** 1 人だと投稿が単調になり、5 人以上は運用できない。
   分ける軸は属性（年齢・性別）ではなく**困りごと**
4. 各人を `personas/<id>.md` の 4 項目で書く — 誰か / 何に困っているか / 刺さる切り口 /
   **この人には響かないこと**
5. **人に見せて確認を取ってから保存する。** 勝手に確定しない
6. `config.yaml` の `content.personas.schedule` への曜日割り当てを提案する
   （書き換えは人が行う）

**「この人には響かないこと」を必ず埋める。** ここが空のペルソナは結局
「みんなに向けた投稿」になり、分けた意味が消える。

#### すでにある場合は見直す

**ペルソナは一度書いたら固定するものではない。** 観測が溜まれば「刺さる切り口」の
記述は実態と食い違っていく。放置すると、**古い読み手像に向けて書き続けることになる。**

`x list` で観測を読んだうえで、4 つの観点で見る。

1. **観測と食い違っている記述**。「刺さる切り口」に書いてある角度が、実際に伸びた
   投稿に出てこない。あるいは伸びた投稿の角度がどのペルソナにも書かれていない
2. **「この人には響かないこと」が空**。分けた意味が消えているので、ここを先に埋める
3. **実測で伸びた自分の投稿がどのペルソナ向けだったか**（`media-agent report`）。
   どのペルソナにも紐づかない投稿が伸びているなら、読み手が 1 人足りていない
4. **1 度も使われていないペルソナ**。`config.yaml` の曜日割り当てから外れたまま
   数週間経っているなら、そのペルソナは運用されていない

**観測が無いうちは見直さない。** 根拠のない書き換えは改善ではなく劣化である。
初回（`structures/` が空で、観測もほとんど無い）は、作成だけ行って見直しは飛ばす。

**変更は提案として出す。`personas/` を勝手に書き換えない。** どの記述を、
どの観測を根拠に、どう変えるかを並べて人に見せ、確認を得てから保存する。
**消す提案にはとくに根拠を付ける** — ペルソナを 1 人減らすと、その人向けの
投稿が今後出なくなる。

**`strategy.md` に書くべき共通事項をペルソナ側に写さない。** トーンや禁止表現は
全ペルソナに効くので、ペルソナに書くと重複して食い違いの元になる。

### 1. 仮説を立てる

**いま何を確かめたいのかを言葉にしてから始める。** 前回から何が変わったか、
どの型が効かなくなったか。ここを飛ばすと、集めた後に何を見ればよいか分からなくなる。

**初回（`structures/` が空）は前回が無いので、次を既定の仮説にする。**
「このジャンルで伸びている投稿には、冒頭の作りに共通の型がある」。
確かめ方は、伸びた群と対照群で冒頭の作りが違うかを見ること。

### 2. クエリを設計する

**クエリ語はどこから取るか。** 思いつきで決めない。

- **自ジャンル側** — `strategy.md` の「コンテンツ方針」で扱うと決めたテーマ語
- **読み手側** — `personas/` の「何に困っているか」に出てくる言葉。**読み手が実際に
  検索する語であって、こちらの業界語ではない**
- **ペルソナ 1 人につき最低 1 本打つ。** 刺さる切り口が人ごとに違うので、まとめて 1 本に
  すると多数派のペルソナに寄る

**各クエリに「何を確かめたくて打つのか」を 1 行添える。** 3 系統を用意する。

| 系統 | 目的 | 枠の配分 |
| --- | --- | --- |
| 自ジャンル・反応あり | 自分の領域で何が効いているか。**題材が読み手に関係するかの確認が主** | 半分以下 |
| 他ジャンル・型の借用 | 文章の型は業界を超える。**題材は借りない** | **半分以上** |
| 対照群 | 伸びなかった投稿 | 同じ引きの中から作る（下記） |

**他ジャンルに枠を厚く取る。** ペルソナ 1 人 1 本を先に埋めると、枠を自ジャンルで
使い切って型の借用が打てなくなる（2026-09-08 の実測で 7 本中 1 本しか打てず、
その 1 本も外れた）。**ペルソナの本数は「題材が読み手に届くか」を確かめるためのもので、
型の供給源ではない。** 自分の領域で表示が大きい投稿は、たいてい題材が違う
（プロテインで伸びるのは筋トレの日常・PR・有名人であって、価格の話ではない）。
**他ジャンルを題材で選ばない。** ここで選ぶのは「その骨組みが強く出ているジャンル」で
あって、「自分の話題に近いジャンル」ではない。**題材の近さで絞ると母集団が小さくなり、
型が取れなくなる**（2026-09-08 の実測: 価格比較が本題のジャンルへ絞り込んだ結果、
1 クエリ 3〜5 件しか返らず、骨格が 0 本になった）。

#### タブは Top（人気順）で取る

**`config.yaml` の `x_reader.search.tab` の既定は `live`（新着順）だが、ベンチマークでは
`top` にする。既定を与件として受け取らない。設定は判断の対象である。**

新着順は「新しい順」なので、**まだ伸びていない投稿しか集まらない。**
「伸びている投稿の型を調べる」という目的と正面から矛盾する。

設定ファイルは live の利点を「検索語に厳密一致するので話題がずれない」と説明しているが、
**2026-09-08 の実測でこれは成立しなかった** — 新着順で `1杯あたり` を引いて、
カジノの無料ドリンク制度・神社の紀行文・12 星座の運勢が返った。
**利点は出ず、欠点（伸びていない投稿ばかり）だけを引き受けることになる。**

```bash
media-agent config set x_reader.search.tab top --account <アカウント>
```

#### 閾値は、目標にしている 1 本の水準から逆算する

**「手が届く範囲の少し上」を「自分と同じ規模の小さい投稿」と読まない。**
ベンチマークの対象は自分と同じ規模の投稿ではなく、**知名度で説明がつかないのに
伸びた投稿**である。前者は低い閾値、後者は「高い閾値 × 高い反応率」で取る。
**低い閾値は、アルゴリズムにまだ一度も試されていない投稿を集める。**

**閾値は固定値ではない。運用アカウントが育てば動かす。** 手順は 3 つ。

1. **いま観測から反応率（いいね ÷ 表示回数）の中央値を出す。** `x list` が各行に出す。
   ジャンルによって違うので、その都度測る
2. **「1 本でこれだけ表示されてほしい」を決める。** 根拠は `strategy.md` の目標。
   流入が要るなら 1 万表示クラス、認知の積み上げなら数千で足りる
3. **割る。** `min_faves ≒ 目標表示回数 × 反応率の中央値`

```
例（2026-09-08 の pergram-jp）
  反応率の中央値 ≒ 0.010
  目標表示回数   = 10,000  （KGI は 14 日で 300 ユーザー = 1 日 21。1 本で効かせるならこの帯）
  → min_faves ≒ 100
```

| | 起きること |
| --- | --- |
| 低すぎる | 目標に届いていない投稿を手本にする。**2026-09-08 に `min_faves:5`（≒ 500 表示）で回し、骨格が 1 本も取れなかった** |
| 高すぎる | 知名度が仕事をしている帯に入る。文章の型ではなくフォロワー数を見ることになる |

**逆算した値の 1〜3 倍の幅で打つ。** 上の例なら `min_faves:100`〜`300`。

**アカウントが育ったら引き直す。** 2 の「目標表示回数」を上げるだけでよい。
`media-agent report` に自分の投稿の実測が出るようになったら、ジャンルの反応率ではなく
**自分の上位の実測**を 1 の根拠にする。**閾値を手順書に固定値で書き込まない** ——
書き込んだ瞬間に、成長したアカウントが自分より小さい投稿を手本にし続けることになる。

#### 対照群は、同じ引きの中から作る

**Top で 1 回引き、その中を表示回数で上下に割る。** 同じ語・同じ期間・同じ閾値のまま
伸びた側と伸びなかった側に分かれるので、比較に他の違いが混ざらない。

**閾値を外してもう 1 回引く取り方をしない。** 閾値は「どれだけ過去まで遡るか」の
つまみとしても働くため、**閾値を変えると集まる投稿の時期が変わる**
（2026-09-08 の実測: 同じ `プロテイン コスパ` で `min_faves:5` は 3 日分、
`min_faves:30` は 9 日分が返った）。時期の違うものを「伸びた vs 伸びなかった」として
比べても、差が何によるものか言えない。

**語は絶対に変えない。** 語を変えると（例: 対照群だけ `プロテイン 高すぎ`）、
比較に話題の違いが混ざる。2026-09-06 の実測でこの取り方をしてしまい、
24 件の観測が使えなくなった。

**効く演算子**: `min_faves:` / `min_retweets:` / `min_replies:` / `lang:` /
`-filter:replies` / `from:<handle>`
**効かない演算子**: `min_impressions:` / `followers_count:`（実測で確認済み。使わない）

**特定のアカウントを読むには `from:<handle>` を使う。** 類似ドメインのアカウントが
何を書いているかは、キーワード検索では取れない — 日常語がジャンル語と重なると、
関係のない雑談が大量に混ざる（2026-09-06 の実測では、`プロテイン min_faves:200` で
返った 6 件のうち本題に関係するものが 0 件だった）。

```bash
media-agent x search "from:<handle> min_faves:50" --account <アカウント>
```

**閾値と併せて打つ。** 新着順タブは「その人の直近の投稿」を返すので、素の
`from:<handle>` だと、伸びたかどうかに関係なく最新のものが並ぶ。
**投稿頻度の低いアカウントでは 0 件で返ることがある**が、それは演算子が
効かないのではなく直近に投稿が無いだけである。

### 3. 観測を集める

```bash
media-agent x search "<キーワード>" --account <アカウント>
```

**打てる本数を先に数える。** 1 クエリ = 検索 1 リクエスト + `expand_top_posts` の件数
（既定 3）で、**既定では 1 クエリが 4 リクエストを使う。**
`pacing.max_requests_per_run`（既定 8）で 1 実行 2 クエリ、
`pacing.max_requests_per_day`（既定 30）で 1 日 7 クエリしか打てない。

**手順 2 の配分を、この本数の中で先に割り振る。** 打ちながら決めると、
自ジャンルで枠を使い切って型の借用が残らない。

```bash
media-agent x doctor --account <アカウント> | grep 経路の状態   # 本日の残りを見る
```

**枠が足りないなら `expand_top_posts` を 1 に下げる**（1 クエリ 2 リクエスト = 1 日 15 本）。
引き換えに、長い投稿の本文が途中で切れることと、連投の続きが繋がらないことが増える。
**設定の変更は人が決める。勝手に書き換えない。**

### 4. 層別と差分を見る

```bash
media-agent x learn --since 7d --account <アカウント>
```

見るもの: 層の件数（S/A/B/C）、提案されたパターンとその n、提案されなかったパターン、
除外件数。**C（対照群）が 0 件なら層別が壊れている。**

**フォロワー数は保存していないので、「権威で伸びただけ」の除外は反応率
（いいね÷表示回数）による代理で行われている。** A 層（表示多 × 反応率低）は
差分から外れている。

### 5. 骨格を抽出する

**本文を全文で読む。** `x status` は近況を見るためのもので本文を 60 字で切るので、
解剖には使えない。**`x list` を使う。**

```bash
media-agent x list --min-impressions <閾値> --limit 20 --account <アカウント>
```

**「伸びた」を先に数字で決める。** 決めずに始めると、目に留まったものを後から
「伸びていた」と言うことになる。**1 回の引きの中で表示回数の中央値を出し、
その 3 倍以上**を伸びた群、残りを対照群とする。閾値は仮説と一緒に書き残す。

**中央値が、手順 2 で決めた「目標表示回数」の 1/10 を下回ったら、そこで止める。**
中央値の 3 倍という規則は、その群がそのジャンルの平常運転を表していることを
前提にしている。**目標が 1 万表示なのに中央値が 225 なら、伸びた群の下限は 675 表示で、
「675 表示で伸びた」は自分の目標にとって何も意味しない**（2026-09-08 の
`個人開発 リリース` がこれだった）。

止めたときにやること:

1. **まず閾値を疑う。** `min_faves` が低すぎると、伸びていない投稿ばかりが母集団になる。
   手順 2 の逆算をやり直す。**ここを飛ばして次へ行かない**
2. **次にタブを疑う。** `x_reader.search.tab` が `live` のままなら Top へ変える
3. **クエリを広げる。** 語が狭すぎて母集団が小さい可能性がある。ジャンル語を 1 段上げる
4. それでも届かないなら、**そのクエリでは骨格を作らない。**
   「観測が足りないので抽出しない」と書き残して次のクエリへ移る
5. **下限を下げて無理に進めない。** 母集団が小さいまま出した「型」は、
   次のクエリで再現しない

#### 層別の単位は「クエリ」ではなく「テーマ」

**Top タブは 1 クエリ 1 ページで 4〜5 件しか返さない**（2026-09-08 の実測: 7 クエリで
3〜5 件ずつ）。**1 クエリでは層別に足りないので、同じ仕事を切り出したクエリを
プールしてから中央値を出す。**

**プールしてよいのは、同じ仕事を切り出せたクエリだけである。** プールする前に
**本文を読んで確かめる。** 語が同じ領域に見えても、返ってきた投稿の仕事が違えば
中央値が壊れる。

2026-09-08 の実測がその例である。`電気代 比較` / `格安SIM 比較` / `ふるさと納税 還元率` /
`業務スーパー コスパ` の 4 本は価格比較の投稿を返した（n=16・中央値 50,494 表示）。
そこへ `サブスク 月額` と `1kgあたり` を足したところ、返ってきたのは価格比較ではなく
**日常のバズ投稿**（サブスクの解約の愚痴 1,284 万表示、セクサロイド論 129 万表示）で、
**プール全体の中央値が 50,494 → 168,814 へ跳ね、本来の候補が全部ふるい落とされた。**

**中央値が跳ねたら、混ぜてはいけないものを混ぜた信号である。** プールを分け直す。

**引きが 10 件を下回ったら、その群からは伸びた群を作れない。** 3 本 3 著者を
中央値の 3 倍より上で満たすには、元が 20〜30 件は要る。4〜6 件しか返らないのは
**閾値かタブか語のどれかが間違っている信号**であって、そのまま分析に進む場面ではない
（2026-09-08 は全 6 クエリが 4〜6 件で、骨格が 1 本も取れなかった）。

**反応率（いいね ÷ 表示回数）がその引き全体の中央値を下回るものは外す。** 表示は多いが
反応が薄いのは、権威やトレンドで運ばれただけで、文章が効いたのではない。
`x list` が各行に反応率を出すのでそこで判断する。

伸びた投稿を **1 本ずつ**解剖して、`structures/<id>.md` に書く。

**ここでは本文を見てよい**（抽出は生成ではない）。**ただし骨格に本文の語句を書かない。**
書いてしまうと、②がそれを読んで他人の投稿の言い換えを出す。

#### 骨格にしてよい条件（4 つとも満たすこと）

1. **3 本以上に現れる。** 1〜2 本は偶然と区別できない
2. **著者が 3 人以上にまたがる。** 同じ人の 4 本は「型」ではなく**その人の癖**である。
   `x list` に出る `@handle` で数える。ここを見ないと、たまたま多く集まった 1 人の
   書き方を X 全体の型だと誤認する
3. **対照群に同じ頻度で現れない。** 伸びた群にも対照群にも等しくあるものは、
   伸びの理由ではなく**そのジャンルの普通**である
4. **題材を入れ替えても成立する。** その骨格を、**固有名詞・製品名・具体的な数値を
   1 つも使わずに**書けるか。書けないなら、それは型ではなく話題である。
   **1 本ずつ**「この投稿の骨組みから題材を抜いたら何が残るか」を 1 行で書く。
   **残るものが本ごとにバラバラなら、その型は採らない。**

**4 が要る理由。** 1〜3 は「同じ骨組みを見ている」ことを暗黙の前提にしていて、
その前提が崩れたときに何も言わない。**数の門は、題材がたまたま揃っただけの群でも通る。**

2026-09-06 の実測がその例である。「改行で縦に箇条書き」という書式が
3 本 / 3 著者（朝食の献立・減量メニュー・韓国チポトレの価格表）で門を通った。
題材を抜くと残るのは「項目を縦に並べる」だけで、**3 本とも運びも締めも別物だった。**
1〜3 だけなら通る。**4 を当てると、残るものがバラバラなので止まる。**

条件を厳しくする方向（3 本 → 5 本）では直らない。**ノイズが 5 本あれば同じことが
起きる。** 見るべきは本数ではなく、**題材を抜いた後に同じ骨組みが残るか**である。

**ここでペルソナを見ない。** 「この型はうちの読み手に刺さるか」は③の判定であって、
①②では使わない。**両方をここで満たそうとすると、他ジャンルの型は構造上すべて落ちる**
——他ジャンルの投稿が自分の読み手の困りごとに触れているはずがないからである。
2026-09-08 に実際にこれで詰まり、価格比較ジャンルへ絞り込む方向で解いてしまった。

`sources` には**本数と著者数の両方**を書く（例: `sources: 5 posts / 4 authors`）。
**`personas` の欄は空のままにする**（③で埋まる）。

#### 長さの上限に収める

**`数値の実体` に書く全体の長さは、自分のアカウントで出せる長さでなければならない。**
無料会員なら**日本語で約 140 字が硬い天井**である（`media-agent knowledge show x/formats` の「長さの上限」）。
余白を見て **135 字以内**で型を作る。

**長い観測から型を取らない。** 300 字の投稿は Premium アカウントのものなので、
無料で運用しているなら写しても再現できない。**自分が出せる長さの投稿だけを解剖する。**

#### 本文だけを見て決められないこと

**観測は本文しか保存していない。画像・動画・スレッドの有無を記録していない。**
画像で伸びた投稿の本文を解剖して「この文章の型が効いた」と結論するのは因果の取り違えで
ある。数字の羅列や比較が本文にあるのに伸び方が不自然に大きいものは、**画像を疑って
骨格から外す**か、`caveats` に「画像の可能性あり」と書いて②に伝える。

書式:

```markdown
---
id: comparison-debunk
name: 常識破壊・対比型
observed_at: 2026-09-02
sources: 5 posts / 4 authors   # 本数と著者数。どちらも下限は 3
impressions: 12000-48000
reaction_rate: 0.011-0.031
targets: [not_dwelled, dwell_time, share_via_dm]
accepts_numbers: yes    # この型は数値の羅列を受け取れるか。yes / no / conditional
personas: []            # ①②では空。③で埋める
---

## 運び（スロット）

1 行目   読者が正しいと思っている前提を名指しで否定 + 結論。20〜25 字。断定
2 行目   （空行）
3 行目   検証した事実を 1 行（「〜を N 件調べた」）。方法は説明しない
4-6 行目 具体的な数値を 2 件、対比の形で縦に並べる。単位を揃える
7 行目   （空行）
8 行目   読者が明日取れる行動で締める。断定せず余韻を残す

## 数値の実体

全体 110〜135 字 / 8 行 / 冒頭行 25 字以内 / 数字の塊 3 箇所以上 /
絵文字 0〜1 個（文末の装飾には使わない）/ URL 無し

## 語の水準（トーン）

常体に口語を混ぜる。一人称なし。断定は冒頭だけ、末尾は緩める。専門語を使わない

## 言い回しの部品

冒頭の作り
- 数値を先に置いて言い切る（「〈数値〉〈単位〉でした」）。理由や前置きを前に出さない
- 読者が正しいと思っている前提を名指しで否定してから結論を置く
- 「〜だと思っていませんか」の問いかけで始めない（結論が後ろに追いやられる）

数値の見せ方
- 単位を先に固定してから数を並べる（「1g あたり」を先に言う）
- 2 件以上を縦に並べ、桁を揃える。文中に埋め込まない
- 最小・中央・最大の 3 点で幅を示す。平均だけを出さない

締めの形
- 読者が明日取れる行動で終える。断定しない
- 問いかけで終える場合は 1 つだけ。2 つ並べない
- 「ぜひ」「参考になれば」で締めない（誰にでも書ける行になる）

## 言わないこと（引き算）

- 挨拶・前置き（「こんにちは」「個人的に気になったので」）を入れない
- 検証の手順や苦労話を書かない
- 免責（「個人差があります」「状況によります」）でヘッジしない
```

**`caveats` は分かったときだけ書く**（画像の可能性、自分の実測と食い違った点など）。

**`accepts_numbers` を必ず埋める。** 共感だけで伸びている型（体験談・あるある）に
数字の塊を入れると壊れる。**④でテーマを流し込むときに選び間違えないための欄である。**
判定は「観測した本数のうち、数字の塊を 2 箇所以上持つものが過半か」で行う。

#### 「言い回しの部品」に何を書いてよいか

**語の水準（トーン）だけでは、書く側は具体的な言い回しを起こせない。**
「常体に口語を混ぜる」から出てくるのは一般論寄りの文である。かといって本文を
写せばパクリになる。**線は「誰のものか」で引く。**

| | 扱い |
| --- | --- |
| 特定の 1 投稿の言い回しをそのまま写す | **入れない。** その人のものである |
| **複数の著者に共通して現れる構文** | **入れてよい。** 誰のものでもなく X で流通している型 |

**この節にも同じ抽出条件が効く**（3 本以上 / 著者 3 人以上 / 対照群に同頻度で
出ない）。**1 本にしか無い言い回しは入れない。**

**構文の水準で書く。** 「1g あたりの最安は ¥1.92 でした」は本文の写しだが、
「数値を先に置いて言い切る」は構文である。**固有名詞・製品名・具体的な数値が
入っていたら、それは写しになっている。**

**抽象度を上げすぎない。** 「読者の興味を引く冒頭」では何も決まらない。
**書く人がそのまま形にできる粒度**で書く。

**「言わないこと」は必須。** 伸びる投稿は、何を書いているかと同じくらい何を削っているかが
徹底されている。ここが空の骨格は未完成として扱い、埋まるまで `structures/` に置かない。

### 6. 自分の実測と突き合わせる

```bash
media-agent report --account <アカウント>
```

**他人で効いた型が、自分でも効いているとは限らない。** 自分の投稿の実測と照合し、
食い違っていればそれを骨格の `caveats` に書く。

**いまは投稿と骨格の紐付けを記録していない。** どの投稿がどの骨格から出たかは
自動では分からないので、**自分の上位の投稿を目で読んで**、採ろうとしている型と
合っているかを見る。ここは機械的な検証ではないと承知して使う。

### 7. 古い骨格を落とす

`observed_at` が古いものを外す。アルゴリズムの構造は不変に近いが、**実際に止まっている
冒頭の作りは数ヶ月で変わる。**

## 報告のしかた

- 作った骨格・更新した骨格を、id と `sources` の件数つきで挙げる
- **骨格にしなかったパターン**と、その理由（件数不足 / 対照群にも同程度 /
  1 本にしか無い言い回しだった）も挙げる
- ペルソナに気づきがあれば `personas/` の更新を提案する（勝手に書き換えない）

## やらないこと

- **投稿を書かない。** それは `/media-draft` の仕事
- **骨格に本文の語句を入れない**
- **`playbooks/` を勝手に書き換えない。** 採用は `media-agent playbook apply` で人が行う
