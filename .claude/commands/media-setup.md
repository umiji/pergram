# セットアップ（対話）

このプロジェクトで Media Agent を使えるようにする。**1 項目ずつ決めて、決まった
そばから CLI で反映する。** config.yaml を直接編集してはいけない — 検証を通らない
値が書き込まれるうえ、設定意図を書いたコメントが消える。

**このコマンドは投稿しない。** 最後まで進めても段階は `test`（ローカルに記録する
だけ）のままで終わる。実配信への切替は人が行う操作であり、ここには含まれない。

## 前提

- 対象アカウントを最初に確認する。以降のすべてのコマンドに `--account <media>/<name>`
  を付ける（例: `x/pergram-jp`）。分からなければ `media-agent accounts` で一覧を出し、
  どれを設定するのか利用者に聞く
- 作業領域がまだ無ければ `media-agent init --account <media>/<name>` を実行する

## 手順

### 1. 現状を機械可読で読む

```
media-agent doctor --json --account <media>/<name>
```

`results` の `status` が `WARN` / `FAIL` の項目が「まだ決まっていないこと」の一覧に
なっている。**これを上から 1 つずつ片付ける。** 別途チェックリストを作る必要はない。

### 2. 秘匿値の置き場を用意する

```
media-agent env init --account <media>/<name>
media-agent env check --account <media>/<name>
```

`env init` は `.env.local` に**キー名だけ**を書き足す。**値は利用者本人が書く。**
利用者に「`.env.local` を開いて値を入れてください」と依頼し、入れ終わったら
`env check` で設定済みかどうかだけ確かめる。**API キーや Cookie の中身を
聞き出したり、ファイルから読み取って画面に出したりしてはいけない。**

### 3. 設定を 1 項目ずつ決める

WARN / FAIL の内容を自然言語で 1 つずつ利用者に聞き、答えを反映する。

```
media-agent config show --account <media>/<name>
media-agent config set connectors.rss.feeds '["https://example.com/feed"]' --account <media>/<name>
media-agent config set content.posts_per_day 3 --account <media>/<name>
media-agent config unset content.similarity_threshold --account <media>/<name>
```

- 値は JSON として読めればその型になる（`true` / `3` / `["a","b"]`）。
  文字列として入れたい数字は `'"3"'` のように引用符を重ねる
- リストは `config show --json` で読んで、要素を足した配列を丸ごと書き戻す
- 検証に落ちたときは終了コード 2 で**何も書かれていない**。値を直して打ち直す

### 4. 棚卸しをする（何があり、何が足りないか）

**ここを飛ばすと、この先で書く `strategy.md` がプロジェクトと結びつかない
一般論になる。** 一般論の上に骨格も投稿も乗るので、後から効いてこない。

#### 4-1. プロジェクトの中身を読む

README・製品の説明・扱っているデータを読む。**何のサービスで、誰の何を解決するのか**
を 2〜3 行にまとめ、利用者に見せて「合っているか」を確認する。

#### 4-2. 目的と目標を人に聞く

**推測で埋めない。** ここを外すと戦略ごと的外れになる。

- **何を達成したら成功か。** フォロワー数か、待機リストの登録数か、問い合わせか。
  **どれを選ぶかで発信の中身が変わる**（フォロワー数なら広く刺さる話題、
  登録数なら購入前の不安を潰す話題に寄る）
- **いつまでに、どれくらいか**（数字が無いなら「無い」と書き残す。勝手に置かない）
- **やらないこと**（触れない話題、名指ししない相手）

プロジェクトから読み取れることと、**聞かないと分からないこと**を分けて提示し、
後者は必ず質問する。

#### 4-3. すでに運用しているアカウントがあるかを確認する

あるなら、実績を取り込む。無いなら飛ばす。

```
media-agent x metrics --account <media>/<name>
media-agent status --account <media>/<name>
```

**過去の投稿があるなら記憶に入れる。** 入れないと重複判定が全件素通りする。

```
media-agent memory import --file <csv> --account <media>/<name>
media-agent memory status --account <media>/<name>
```

#### 4-4. 足りないものを一覧で出す

**`doctor` は設定の検査であって、戦略の欠落は見ない。** 次を人に見せる。

| 足りないもの | 確かめ方 | 埋め方 |
| --- | --- | --- |
| 目的・目標 | 4-2 で聞けたか | この手順の中で人に聞く |
| 読み手（ペルソナ） | `personas/` が空か雛形のまま | 手順 5 で作る |
| 運用戦略 | `strategy.md` に「（未記入）」が残っているか | 手順 5 で埋める |
| 過去投稿の記憶 | `media-agent memory status` が 0 件か | 4-3 の `memory import` |
| 素材 | `materials/` が空か | `/media-draft` の手順 5 で掘る |
| 骨格 | `structures/` が空か | `/media-method` |
| 承認済みの戦略（Phase 2） | `media-agent strategy list` に `*` が無い | `/media-strategy` |

**空のまま先へ進めてよいものと、進めてはいけないものを区別して伝える。**
読み手と `strategy.md` が空のままだと、この先の生成は誰にも刺さらない。
素材と骨格は無くても一般則で書けるので、後回しでよい。

### 5. 戦略・ルール・ペルソナを書く

`strategy.md` と `rules.md` は設定項目ではなく本文なので、対話で内容を固めてから
ファイルに直接書く。置き場所は `media-agent config show` が出す設定ファイルと
同じディレクトリ（`.media-agent/<media>/<name>/`）。

- `strategy.md` — 何のアカウントで、誰に、何を届けるのか
- `rules.md` — 書いてはいけないこと、口調、禁止表現
- `personas/<id>.md` — 読み手。**曜日で変えるかどうかに関係なく最低 1 人は要る**

**ここで作るのは「誰に・何を・どの頻度で」であって、「どう書くか」ではない。**
文章の型（骨格）は `/media-method` の仕事なので、ここでは踏み込まない。

#### 5-1. 読み手を決める

4-2 で聞いた目標から逆算する。**属性ではなく、その人がいま置かれている状況**で書く。

- 困りごとで 2〜4 人に分ける（人数ではなく**困りごとの種類**で分ける）
- 1 人ずつ「いまどういう状態で X を見ているか」を 1〜2 行で書く
- **人に見せて確認を取ってから** `personas/<id>.md` に保存する

#### 5-2. 似たサービスと実アカウントを調べる

**何を見るかを先に決める。** 漫然と眺めても戦略にならない。

1. **似たサービスを 3〜5 個挙げる**（同じ困りごとを扱っているもの。同じ業界とは限らない）
2. それぞれの X アカウントを特定し、**`from:<handle>` で実際の投稿を読む**

   ```
   media-agent x search "from:<handle> min_faves:20" --account <media>/<name>
   media-agent x list --limit 20 --account <media>/<name>
   ```

3. 各アカウントについて次を 1 行ずつ書く
   - 誰に向けているか / 何を約束しているか / どの話題を**扱っていないか**
   - どの投稿が伸びているか（**表示回数と反応率の両方**を見る）

**扱っていない話題は、空いている場所である。** そこが自分の立ち位置の候補になる。

**出典を必ず残す。** 「そう決めた」の根拠が無い記述は、次に読む人が検算できず、
数週間後には誰も理由を言えなくなる。`strategy.md` に**見た日付とアカウント名**を書く。

**本文をそのまま転記しない。** 転記すると、後の工程がそれを読んで言い換えを出す。
書くのは「何をしているか」の要約であって、文そのものではない。

#### 5-3. 頻度と時間帯を決める

**根拠つきで決める。** 勘で置くと、後から変えるときに何を変えたのか分からない。

```
media-agent knowledge show x/discovery-distribution --account <media>/<name>
```

- **短時間の連投は自分で自分を潰す。** 同一閲覧者のセッション内で、同じ著者の
  2 件目以降には減衰がかかる。**1 日に複数本出すなら時間を空ける**
- 読み手が X を見る時間帯に合わせる（5-1 で書いた「いまどういう状態で見ているか」）
- **続けられる頻度にする。** 週 3 本を守るほうが、週 7 本で止まるより効く

決めたら `strategy.md` の「投稿方針」に**理由つきで**書く。

#### 5-4. 曜日ごとの読み手の割り当てを決める

読み手を曜日で変えるなら、`config set` を通して入れる。**直接編集しない。**

```
media-agent config show --json --account <media>/<name>
media-agent config set content.personas.schedule '{"mon":"<id>","wed":"<id>","fri":"<id>"}' --account <media>/<name>
```

割り当てない曜日があってよい。**無理に埋めない。**

#### 5-5. 「（未記入）」を残さない

書き終えたら `strategy.md` を読み直す。**「（未記入）」が 1 つでも残っていたら、
そこは決まっていない。** 決められないなら「まだ決めていない」と理由つきで書く。
**空欄と「決めていない」は別物である** — 空欄は次に読む人に「書き忘れ」と読まれる。

### 6. Phase 2 の戦略を作るかを伝える

`strategy.md` は**材料**である。ここから**版のついた運用戦略**（柱・配合比・実験）を
作る経路が別にある。

```
media-agent strategy build --account <media>/<name>
```

**この手順の中では実行しない。** Provider を呼ぶので費用がかかり、
`strategy.md` が固まってからでないと薄い版ができる。`/media-strategy` を案内し、
**やるかどうかは利用者が決める。**

### 7. 通ったことを確認して終わる

```
media-agent doctor --account <media>/<name>
media-agent mode show --account <media>/<name>
```

FAIL が 0 件になったら完了。**段階は `test` のまま終える。**

最後に利用者へこう伝える。

- いまは `test`（ローカルに記録するだけ・外部に何も出ない）であること
- 生成を試すには `/media-draft`、動作の確認には `/media-status` が使えること
- 版のついた運用戦略を作るなら `/media-strategy`、そこから候補を作るなら
  `/media-content` があること（**どちらも投稿しない**）
- 外部に出す段階へ上げるかどうかは人が決める操作であり、必要になったら
  `media-agent mode show` で選択肢を確認したうえで利用者自身が切り替えること

## やってはいけないこと

- config.yaml / `.env.local` を直接書き換えること（CLI を通す。`.env.local` は人が書く）
- 秘匿値の中身を読み取る・表示する・要約すること
- 段階を `test` より外に出す操作を、利用者に頼まれていないのに実行すること
- `media-agent run` や `media-agent post` をこの流れの中で実行すること
- **目的・目標を推測で埋めること。** 聞かないと分からないことは必ず人に聞く
- **リサーチの結果を出典なしで `strategy.md` に書くこと**
- 競合アカウントの投稿を**本文のまま**転記すること
- **骨格（どう書くか）をここで作ること。** それは `/media-method` の仕事である
